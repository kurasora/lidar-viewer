## 見つけた問題

### R4-001 [中] 複数ファイルを関連付けで同時に開くと、半分前後が黙って開かない（新機能の競合）
- 種類: バグ / 使い勝手
- 対象: アプリ版（全 OS。関連付け・「このアプリで開く」で複数ファイルを選んだとき）
- 再現手順:
  1. 製品版を起動しておく（単一インスタンス）。
  2. 点群ファイルを複数、ファイルマネージャで選んで「LiDAR Viewer で開く」等で続けて開く（OS はファイルごとに別プロセスを起動し、それぞれが second-instance として届く）。
  3. 再現: `$T/work/R4/regress/burst_test.js`（実プロセスを 8 個、間隔なしで連続起動）。
- 期待される結果: 渡した 8 ファイルがすべて開く。
- 実際の結果: 8 個のうち 4 個しか開かず（m001・m006・m007・m008）、主プロセスのコンソールに `ファイルを渡せませんでした: target closed while handling command` が 4 回。画面側には何の知らせも出ない（statMsg は更新されない）ので、ユーザーは「一部が消えた」ことに気づけない。
  （synchronous に second-instance を 12 連発した `race_test.js` では 1/12 しか開かなかった）。
- 場所: main.js の `openPaths()`（83〜108 行あたり）。
- 原因の見立て: `openPaths` が呼ばれるたびに `pendingPaths.splice(0)` で全件を取り出し、`mainWin.webContents.debugger` を attach→DOM.setFileInputFiles→detach する。second-instance が短時間に重なると、(a) 同じ隠し input に別の呼び出しが上書きし合う、(b) 先に終わった呼び出しの `dbg.detach()` が、まだ await 中の別の呼び出しの最中に走り「target closed」で失敗する。再入可能になっていない。
- 直し方の案: openPaths を直列化する（処理中フラグ＋キューで 1 件ずつ、または全 pending を 1 回の setFileInputFiles にまとめる）。debugger の attach/detach は処理の全区間で 1 回だけにする。失敗時は画面に「N 個のうち M 個を開けませんでした」と知らせる。
- 確度: 再現済み（実プロセスの連続起動で 4/8。タイミング依存で、1 プロセスに全ファイルを argv で渡す経路は正常）。
- 再現スクリプト: `$T/work/R4/regress/burst_test.js`・`race_test.js`

### R4-002 [軽微] 同じファイルをパスと file:// URI の両方で渡すと二重に開く
- 種類: 意図しない挙動
- 対象: アプリ版（コマンドライン・関連付け）
- 再現手順: 起動引数に `スペース 日本.pcd` と `file://…/スペース 日本.pcd` を両方渡す（`argv_test.js`）。
- 期待/実際: 期待は 1 回。実際は同じ点群が S.files に 2 つ入る（重複して描画・一覧に並ぶ）。
- 場所: main.js `filesFromArgv`（73〜89 行）。resolve 後に重複除去していない。
- 直し方の案: `filesFromArgv` の戻り値を正規化パスで de-dup。openPaths でも既出パスを弾くと安全。
- 確度: 再現済み（ただし通常 OS は同一ファイルを 2 形式で同時に渡さないため、実被害は小さい）。
- 再現スクリプト: `$T/work/R4/regress/argv_test.js`

### R4-003 [軽微] deb に連絡先・配布元のプレースホルダが入ったまま 0.4.0 として同梱
- 種類: 配布物 / 文言
- 対象: Linux deb（amd64・arm64）
- 実際の結果: control の `Homepage: https://localhost/lidar-viewer`、`Maintainer/Vendor: fukuda <fukuda@localhost>`、/usr/share/doc/lidar-viewer/copyright の `Source: (配布元の URL をここに / project URL)`。`apt show lidar-viewer` でそのまま表示される。
- 場所: package.json（homepage・author.email・linux.maintainer）、build/linux/copyright。
- 原因の見立て: F6 で「実在値が不明なため仮のまま。作者が書き換える」と明記済みの既知事項。公開配布前に未記入だと見栄えが悪いので、リリース前チェックとして再掲。
- 直し方の案: 実際の配布 URL・連絡先に置換（electron-builder は homepage 必須）。
- 確度: 再現済み（既知・設計上の TODO）。

### R4-004 [情報] 試作ページに charset/viewport/CSP/doctype がなく、claude.ai の枠に依存
- 種類: 配布物（公開時の注意）
- 対象: 試作ページ（dist-artifact/pcd-viewer.html）
- 実際: build.mjs の artifact 出力は `<title>`＋`<style>`＋body＋`<script>` だけで、src/index.html にある `<!doctype>`・`<meta charset=utf-8>`・viewport・`Content-Security-Policy`（`'unsafe-eval' wasm-unsafe-eval blob: worker-src blob:`）・color-scheme を落とす。claude.ai のアーティファクト枠はこれらを外側で付けるので枠内では正常（本試験でも別オリジン sandbox＋charset 骨組みで 72/73 サンプルが動作）。
- リスク: このファイルを claude.ai の枠を通さず素の HTML として配る/別ホストで開くと、(1) charset 宣言がなく日本語 UI が文字化けしうる、(2) STEP の eval・blob worker・wasm を枠側 CSP が止めると一部形式が読めない。
- 直し方の案: 公開時は claude.ai のアーティファクトとして配る前提を手順に明記。単体配布も想定するなら artifact 出力の先頭に doctype＋charset＋viewport を付けておくと安全（CSP は claude 側と二重でも可）。
- 確度: コード確認（build.mjs 41〜54 行）。

### R4-005 [情報] ライブ配信の総当たり対策・受信フレームまわりの小さな懸念（コード推定）
- 種類: セキュリティ / 性能（いずれも LAN 内・自発接続が前提で低リスク）
- 対象: live.js
- (a) Sharer.verify の失敗回数 Map `this.bad` は IP ごとに増え、成功時以外に期限切れ掃除がない。異なる送信元 IP が多いと増え続ける（LAN では台数が上限なので実害小）。
- (b) 合言葉は 4 桁・同一 IP 5 回/60 秒でロックだが、60 秒窓でカウンタが 0 に戻るため持続的に 5 回/分＝全数（1 万）まで約 33 時間。LAN 用途なら許容範囲だが、桁を増やすか指数バックオフにすると堅い。
- (c) 受信側 peer のフレーム上限 MAX_FRAME=64MB。悪意ある配信元に繋ぐと decodeBatch が 64MB の copy＋Float32 の slice（約 2 倍）を高レートで確保し、受信側メモリを圧迫しうる（配信元に自発的に接続した場合のみ）。
- 直し方の案: (a) bad の古い項目を定期削除し件数上限。(b) 合言葉の桁数増 or バックオフ。(c) peer 受信フレームの上限を実データ相当（数 MB）に下げる。
- 確度: コード上の推定（live.js 311〜325・300〜309・474 行）。
