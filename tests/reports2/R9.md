## 見つけた問題

### R9-001 [重大] 覚えた合言葉が、hid を名乗るだけのなりすまし配信へ無言で送られる（LAN で合言葉を抜ける）
- 種類: セキュリティ（情報漏えい／なりすまし。新機能「合言葉の保存」起点）
- 対象: アプリ版（ライブ。全 OS）。STRIDE: Spoofing / Information Disclosure
- 背景: 0.4.0 は一度通った合言葉を `live.json` の `peerCodes[hid]` に保存し、次からは hid が一致する配信に**合言葉を自動で送って**つなぐ（確認なし）。hid（＝配信元の hostId）は beacon に平文で載って LAN にブロードキャストされ、B28 の注記どおり **beacon のなりすましは今も防いでいない**。
- 再現手順（`$W/poc/poc_hid_harvest.js`、本物の live.js を使用・ループバック）:
  1. 被害者が過去に本物のホスト（hid=`host-abc-123`）へ合言葉 `7391` でつなぎ、`peerCodes` に保存済み、という状態を作る。
  2. 攻撃者が LAN で本物の beacon から hid を読み取り、同じ hid・`auth:1`・port=攻撃者の WS を指す beacon を流す（PoC では finder.peers に同等のエントリを注入）。被害者の一覧に本物と同じ名前の配信が出る。
  3. 被害者がその配信の「表示」を押す（合言葉は入力しない）。
- 期待される結果: 保存した合言葉を、相手が本物（検証済み）のときだけ送る。少なくとも接続先 IP が前回と違えば確認する。
- 実際の結果: `startPeer` が `known = peerCodes[p.hid]` を取り出し、`ws://攻撃者/?code=7391` に**無言で**接続。攻撃者の WS サーバが `?code=7391` を受け取る（`$W/evidence/hid_harvest.txt`: `attacker captured code = "7391"`）。攻撃者は抜いた合言葉で**本物のホストの配信**（室内形状の点群）を受信できる。
- 場所: live.js:470-478（`known = this.store.data.peerCodes[p.hid]`／`use = code ?? known`／URL に `?code=` で付与）、live.js:380（beacon の hid をそのまま peer 化）、live.js:344（配信側が hid を平文で broadcast）。
- 原因の見立て: hid が「公開・なりすまし可能」なのに、合言葉を送ってよい相手の識別子として使っている。接続先の正当性（IP・鍵交換）を見ずに保存合言葉を送る。
- 直し方の案: 保存合言葉を送る前に接続先 IP が前回保存時と同じか確認し、違えば再入力を促す。hid だけで自動送信しない。恒久的には beacon に署名/チャレンジを入れ hid のなりすましを無効化（B28 の積み残し）。
- 確度: 再現済み（ループバックで合言葉の流出を実証）。実 LAN での beacon 読み取り→なりすましは B28/A08-005 で既に実証済みの経路。
- 再現スクリプト: `$W/poc/poc_hid_harvest.js`

### R9-002 [中] 4 桁合言葉の総当たり対策が「IP ごと」で、IP を増やせば数分で全数（R4-005(b) の実用的な回避）
- 種類: セキュリティ（認証の総当たり）。STRIDE: Spoofing（なりすまし）
- 対象: アプリ版（配信の合言葉）
- 再現手順（`$W/poc/poc_verify_and_b01.js`、本物の `Sharer.verify` を直接呼ぶ）:
  - 同一 IP から 6 連続で誤り → 1〜5 回目 401、6 回目 429（ロック）。ここまでは仕様どおり。
  - **別の IP から誤ると即 401**（ロックされない）。`this.bad` は `req.socket.remoteAddress` を鍵にしているため、送信元 IP ごとに 5 回の枠が独立する（`$W/evidence/verify_b01.txt`）。
- 期待される結果: 合言葉が 4 桁（1 万通り）でも、LAN の第三者が現実的な時間で当てられないこと。
- 実際の結果: LAN の攻撃者は自分の NIC に副 IP を複数割り当てる（`ip addr add` 等）だけで枠を増やせる。/24 で ~254 個使えば **5×254=1270 回/分** → 1 万通りを **約 8 分**で全数。R4-005(b) の「33 時間」は同一 IP 前提で、実際はこの回避で大幅に短い。
- 場所: live.js:313-320（`verify`: `this.bad` のキーが IP のみ／件数の全体上限なし）。
- 原因の見立て: レート制限が送信元 IP 単位だけで、全体のレート上限・指数バックオフ・合言葉の桁数が不足。
- 直し方の案: 全体の失敗レート上限（IP 非依存）を併用、桁数を増やす（6 桁＋英字）、失敗ごとの指数バックオフ、`this.bad` の件数上限と掃除（R4-005(a)）。
- 確度: 再現済み（verify が IP ごとにロックすることを実証）／副 IP での全数は計算に基づく推定（LAN で容易）。
- 再現スクリプト: `$W/poc/poc_verify_and_b01.js`

### R9-003 [軽微] live.json が平文・誰でも読めるパーミッションで保存される
- 種類: セキュリティ（ローカルの情報漏えい）
- 対象: アプリ版（全 OS。userData/live.json）
- 実際の結果: `loadStore.save` は `fs.writeFileSync(file, JSON.stringify(data))`（live.js:547）。umask 0022 の環境でモード **0644（-rw-r--r--）**、中身は `{"shareCode":"8990","hostId":...,"peerCodes":{...}}` と**平文**（`$W/ud/vf/live.json` で確認）。自分の配信の合言葉と、保存した相手の合言葉が、同じ PC の他ユーザーから読める。
- 期待される結果: 資格情報を含むファイルは本人のみ読める（0600）。
- 原因の見立て: 書き込み時のモード指定なし。
- 直し方の案: `fs.writeFileSync(file, json, { mode: 0o600 })`。可能なら合言葉は保存しない/都度入力、または OS の資格情報保管に寄せる。
- 確度: 再現済み（パーミッション・平文を確認）。実被害は共有 PC 限定で軽微。
- 証拠: `$W/ud/vf/live.json`

### R9-004 [情報] 開発者ツールを開いている間、関連付けで渡したファイルが無言で開けない
- 種類: 意図しない挙動（関連付け経路の堅牢性）
- 対象: アプリ版（`app.isPackaged=false` または環境変数 `LIDAR_VIEWER_DEVTOOLS=1` で F12→DevTools を開いた状態のみ）
- 見立て: `openPaths` は `webContents.debugger` を attach→`DOM.setFileInputFiles` で隠し input に入れる（main.js:91-106）。DevTools のフロントエンドが開いていると CDP が既に占有され、`dbg.attach('1.3')` が「Another debugger is already attached」で例外→catch で `console.error('ファイルを渡せませんでした')` のみ。画面には何の知らせも出ず、関連付け/「このアプリで開く」が無反応になる。`dbg.isAttached()` は DevTools 占有を検知しない。
- 期待される結果: DevTools が開いていてもファイルが開ける（別経路）、または画面に失敗を知らせる。
- 直し方の案: attach 失敗時に画面へ知らせる。恒久的には CDP 注入でなく preload の安全な受け渡しに替える。製品版（F12 無効）では通常起きない。
- 確度: コード上の推定（Electron+xvfb の実機再現は未実施。製品版の既定では無効なため低優先）。
- 場所: main.js:91-106。
