### R17-002 [軽微] mcap のメッセージ符号化（message_encoding）を確かめないため、protobuf などの別符号化でも schema 名が ROS 2 と同じなら CDR として読み、ごみの姿勢を「軌跡」として開く

- 再現: `$W/data/pb_odom_ros2name.mcap`（schema 名 `nav_msgs/msg/Odometry`・encoding protobuf、300 メッセージ、中身の 2 バイト目が 0x01）

- 期待: message_encoding が `cdr` 以外なら読まない。読めたメッセージが全体の一部（例: 半分未満）なら知らせる。姿勢 1 つは軌跡として断る。

- 確度: 再現済み（Node。実際に protobuf で Odometry という名前を付ける記録器はまれなので、軽微）

### R17-003 [中] 色分けの「項目」を切り替えるたびに、前の項目の GPU バッファが消されずに残る（ファイルを閉じても残る）
- 種類: リーク（GPU メモリ）／対象: 両方
- 再現: `cd $W/regress && $T/bin/heavy node leak.js`（WebGL の createBuffer/deleteBuffer/bufferData を数える）。`sample/map.laz`（36 万点）を開き、色分けを「項目」にして intensity ⇔ classification を 10 回切り替え、ファイルを閉じる。
- 期待: 切り替えても GPU のバッファは 1 本（項目の値）を入れ替えるだけ。閉じたら全部消える。
- 実際: 開いた直後 5 本 4.1 MB → 項目 6 本 5.5 MB → 10 回切り替え後 15 本 17.9 MB（1 回ごとに 1.4 MB＝点数×4 バイトが増える）→ 閉じた後も 13 本 12.4 MB（deleteBuffer は 2 回だけ）。1 億点のファイルなら 1 回の切り替えで 400 MB の VRAM が戻らず、何度か切り替えると GPU のメモリが尽きて WebGL の文脈が失われ得る（→ R11-003 の状態の初期化につながる）。
- 場所: src/app.js:614 `f.geom.setAttribute('scalar', …)`。three.js r160 の WebGLGeometries は geometry.dispose 時に「今付いている」属性しか消さず、setAttribute で置き換えた古い属性の GL バッファは消さない（three.module.js:17395-17410）。
- 直し方の案: 置き換える前に古い属性の GL バッファを消す（`renderer.attributes.remove(old)` は内部 API なので、同じ大きさなら `old.array = vals; old.needsUpdate = true` で中身だけ入れ替える＝バッファを使い回す。freeAfterUpload と両立させるなら、`vals` を一時的に入れて `needsUpdate` → onUpload で捨てる）。
- 確度: 再現済み（Chromium＋SwiftShader。GPU の実メモリは実機で要確認）

### R17-004 [中] 床と「45° の斜めの天井（屋根裏・A 型の小屋）」だけの地図を 10〜20° 傾けて手動で補正すると、屋根の面を床とみなして約 33° 回してしまう（上向きの誤差 45°）
- 種類: 意図しない挙動（黙って誤る）／対象: 両方
- 再現: `$T/bin/light python3 $W/lv/gen17.py $W/lv && $T/bin/light python3 $W/lv/eval17.py $W/lv`（worker.js の analyze を R10 の切り出し `lv/analyze.mjs` で実行。正解付きの面を numpy で作る）。`attic45ng_12`: 床 12×8 m＋両側の 45° の屋根面（妻壁なし）を傾き約 13°（x 12°・y 6°）・ヨー 25° で回したもの。
- 期待: 上向きの誤差が数度以内、または「向きを決められません」で断る。
- 実際: 「傾き 33.45° を補正」、上向きの誤差 44.97°、床の高さ -2.920 m（正解 -1.2）。同じ形で傾き 0°/約 6.7° なら「傾きが大きすぎて（約 45°/39°）」で断る（＝傾きが大きくなるほど誤った答えを出す）。自動補正（maxTilt 20°）では断るので、ボタンで補正したときだけ起きる。
- 他の形（問題なし）: 2 階建て（1F・2F の床・吹き抜け・15 段の階段、原点が 1F／2F で 2F の点が多い、傾き 0/6.7/13.4°）は上向きの誤差 ≤0.01°・床は原点の真下の階の床（±3 mm）。妻壁のある屋根裏・両端に壁のある 10° の台形トンネルも誤差 ≤0.01°。端の壁のない台形トンネルは「直交する面が少なく」で断る（正しい）。
- 場所: src/worker.js analyze（1 本目の軸 d0 は「平行＋直交の面が最も多い向き」。互いに直交する 2 枚の 45° の屋根面が床より多いと d0 が屋根の法線になり、2 本目も屋根、3 本目は水平になる。その 3 本から「z に最も近いもの」を上とするので、傾けると片方の屋根の法線が 35° 以内に入って採用される）
- 直し方の案: d0・e2・e3 のうち上に選ぶ軸の「平行な面の点数（床・天井らしさ）」が他の 2 本と比べて十分か、選ばれた上向きに直交する面（壁）があるかを確かめる。または候補ごとに findFloor が床を見つけられるか（床のピークが原点の下にあるか）で選ぶ。少なくとも、選んだ上向きで findFloor した床が「原点の下の、上向きに平行な面」になっているか（この例では屋根面の下に床の点があり、床のピークが屋根面に当たらない）を確かめ、合わなければ「向きを決められません」で断る。
- 確度: 再現済み（Node で analyze を直接。実際の屋根裏の地図で起きるかは推定）

## まとめ
- 範囲と技法: (1) 複数ファイルの tbounds（f.tbox）を、別スレッドに単位でない行列で全点を聞いた正解と突き合わせ（状態遷移: 片方非表示→補正→表示→もう片方非表示→設定のすばやい切替→元に戻す）。(2) 正解付きの合成地図（2 階建て・吹き抜け・階段、屋根裏 45°（妻壁あり/なし）、10° 内倒れの台形トンネル（端の壁あり/なし）× 傾き 0/6.7/13.4°）で worker の analyze を実行。(3) freeAfterUpload 後に全点の写しを前提にする箇所のコード網羅（app.js の attributes/array/sample の全使用箇所）と、WebGL のバッファの作成・削除の計数。(4) LAS（スケール 0.01〜0.0001・オフセット ±3e7・1e9・z だけ 1e7・int32 の端）と E57（姿勢の平行移動 ±3e7）を Node で全点照合、Chromium でクリックして選んだ点を元の点と照合。(5)(6) map.laz＋trajectory.txt で補正あり/なし/文脈復帰後の「軌跡の点→最寄りの点群の点」距離と「軌跡に沿って動かす」の中心。(7) ROS1・JSON・protobuf 風の mcap。(8) Electron で renderer を人工的に 2〜4 秒詰まらせて OS から 3 回開く。
- 見つけた数: 致命 0 / 重大 0 / 中 2（R17-003・004）/ 軽微 3（R17-001・002・005）/ 情報 0
- 問題なかったこと:
  - (1) tbounds: 7 つの状態すべてで S.boundsTrue が正解と完全一致（差 0）。非表示のファイルは要求せず、表示したときに要求される。補正の設定を 30 ms 間隔で 6 回切り替えても、古い行列の返事は捨てられ最後の行列の値になる。キーが行列の文字列なので、行列が A→B→A と戻っても取り違えない。
  - (2) 2 階建て（原点が 1F/2F、2F の点が 2 倍）・階段・妻壁のある屋根裏・端の壁のある台形トンネルは上向きの誤差 ≤0.01°、床は原点の真下の階（±3 mm）。2 本目の軸（R3-001 の方式）は階段の段鼻・蹴込みでも乱れない。
  - (3) freeAfterUpload の後に全点を使う箇所は画面側にない（全点が要る計算は tbounds/pick/analyze/field で別スレッド）。標本 f.sample を使うのは範囲・色・デモ（デモは 40 万点→20 万点に減るだけ）。画像の保存は同じ WebGL の文脈から drawImage するので点が欠けない。WebGL 復帰は開き直し（R11-003 のとおり状態は初期化）。残っていたのは GPU 側のリーク（R17-003）。
  - (4) LAS 1e7・-3e7・1e9・z=1e7・int32 端・E57 の姿勢 ±3e7: 読み込みの誤差 ≤0.061 mm（Float32 の刻み）、クリックで選んだ点の座標は元の点と ≤0.061 mm、表示値（小数 3 桁）は丸め以内（≤0.7 mm）。オフセットは 100 m 単位で負にも正しく付く。
  - (5) 補正あり/なし/文脈復帰後で、軌跡の 30 点から最寄りの点群の点までの距離は完全に同じ（差 0.0000 m、最大 0.291 m・中央 0.239 m）。補正後、軌跡の高さの中央値は床（1 % 点 -0.448 m）より約 0.42 m 上＝センサーの高さで妥当。「軌跡に沿って動かす」の中心は、軌跡を world 行列で動かした位置と一致（ずれ 0 m、補正あり/なし/復帰後）。
  - (6) 文脈復帰後も軌跡は残り（頂点 7077 個のまま）、自動補正が同じ傾き（3.372°）で掛かり直して点群と重なる。ピンは消える（R11-003 の既知）。
  - (8) renderer を 4 秒詰まらせて 700 ms・300 ms 間隔で 3 回、2 秒ずつ 3 回詰まらせながら開いても、3 つとも開く（CDP の setFileInputFiles が renderer の空くのを待ち、主プロセスの 1 回ずつの鎖で順序が保たれるため上書きは起きない）。R11 の「まだ見ていない観点」の上書き競合は再現せず。
