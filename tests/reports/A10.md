## 見つけた問題（途中経過。最後に並べ直す）

### A10-001 [致命] Ubuntu 24.04（ROS2 Jazzy の標準 OS）で deb 版・AppImage 版が起動直後に落ちる。エラーの指示どおり chrome-sandbox を 4755 にしても、置き場所「/opt/LiDAR Viewer」の空白のせいでやはり落ちる
- 種類: 配布物 / バグ
- 対象: アプリ版（Linux x64・arm64 の deb と AppImage）。Ubuntu 23.10 以降（24.04 LTS を含む）など、一般ユーザーの user 名前空間を制限している OS
- 再現手順（このマシンで、Ubuntu 24.04 の制限を seccomp でまねて再現。`$W/regress/linux_sandbox_test.sh`）:
  1. deb と同じく `/opt/LiDAR Viewer/` に linux-unpacked を置く（専用のマウント名前空間で /opt に重ねる）
  2. deb の postinst と同じ判定を root で実行 → `unshare --user true` が root では通るので **0755**（SUID にしない）と判定される
  3. 一般ユーザー（uid 999）で、user 名前空間を作れない状態（`$W/bin/nouserns`）で `/opt/LiDAR Viewer/lidar-viewer` を起動
  4. エラーの指示どおり `chown root:root` + `chmod 4755 chrome-sandbox` にして、もう一度起動
- 期待される結果: 起動する（どちらかのサンドボックスで）
- 実際の結果（`$W/evidence/sbx_result.txt`）:
  - 手順 3（0755）: `FATAL:setuid_sandbox_host.cc(163)] The SUID sandbox helper binary was found, but is not configured correctly. Rather than run without sandboxing I'm aborting now. You need to make sure that /opt/LiDAR Viewer/chrome-sandbox is owned by root and has mode 4755.` → 終了
  - 手順 4（4755）: `LaunchProcess: failed to execvp: /opt/LiDAR` と `FATAL:zygote_host_impl_linux.cc(207)] Check failed: . : Invalid argument (22)` → 終了（**パスが空白で切れている**）
  - 対照: 同じ 4755 でフォルダ名を空白なし（`/opt/LiDARViewer`）にすると SUID サンドボックスで正常に起動（描画プロセスが別の PID 名前空間に入っている）。user 名前空間が使える普通の環境（Ubuntu 22.04・Debian 12・Raspberry Pi OS 相当）では 0755 のままで起動する。`--no-sandbox` なら制限下でも起動する
- 証拠: `$W/evidence/sbx_result.txt`、`$W/evidence/sbx_B_space_0755_userns_ng.log`、`$W/evidence/sbx_C_space_4755_userns_ng.log`、`$W/evidence/sbx_D_nospace_4755_userns_ng.log`
- 場所: deb の postinst（electron-builder 25.1.8 の雛形。`unshare --user true` を root で実行して判定）／package.json:3,21 の productName「LiDAR Viewer」が /opt のフォルダ名になる（空白入り）／Chromium の `CommandLine::PrependWrapper` が SUID ヘルパーのパスを空白で分割する
- 原因の見立て: Ubuntu 23.10 以降は AppArmor（`kernel.apparmor_restrict_unprivileged_userns=1`）で、プロファイルのないアプリの user 名前空間を制限する。postinst は root で判定するので制限に気づかず SUID を付けない。AppImage は読み取り専用の FUSE の中なので SUID にできず、ファイルをダブルクリックすると AppRun は `--no-sandbox` なしで起動する（`--no-sandbox` は AppImage 内の .desktop の Exec にだけ付いている）。外部の同種の報告（Ubuntu 24.04 の Electron アプリで同じ 2 つのエラー）: https://community.vikunja.io/t/linux-desktop-app-install-problems/3614
- 直し方の案: (1) `linux.executableName` とは別に /opt のフォルダ名を空白なしにする（productName を `LiDAR-Viewer` などにするか、deb の `afterInstall` で作り直す）。(2) postinst を「AppArmor の制限があれば（`/proc/sys/kernel/apparmor_restrict_unprivileged_userns` が 1）SUID にする」か、`/etc/apparmor.d/lidar-viewer` に `profile lidar-viewer "/opt/LiDAR*Viewer/lidar-viewer" flags=(unconfined) { userns, }` を置いて `apparmor_parser -r` する（Chrome・VS Code の deb と同じやり方）。(3) AppImage は利用者向け手順に「Ubuntu 24.04 では `--no-sandbox` を付けて起動」を書くか、deb を勧める
- 確度: 再現済み（制限は seccomp でまねたもの。本物の Ubuntu 24.04 での確認は実機手順 L-1）
- 再現スクリプト: `$W/regress/linux_sandbox_test.sh`（`heavy xvfb-run -a -n 200 -s "-ac -screen 0 1280x800x24" bash linux_sandbox_test.sh <linux-unpacked> <作業フォルダ>`）

### A10-002 [中] deb・AppImage のアイコンが 1024x1024 の 1 枚だけで、GTK（GNOME のメニュー・ドック）がアイコンを見つけられない（0.2.0 からの後退）
- 種類: 配布物
- 対象: アプリ版（Linux の deb x64/arm64、AppImage）
- 再現手順: deb を展開し、Ubuntu 24.04 の hicolor テーマ（hicolor-icon-theme 0.17）で GTK 3.24 の `gtk_icon_theme_lookup_icon("lidar-viewer")` を呼ぶ（`$W/regress/gtk_icon_lookup.py`）
- 期待される結果: 16〜512 の各大きさで Tsubu のアイコンが見つかる
- 実際の結果: `has_icon: false`、どの大きさでも `null`。パッケージに入っているのは `usr/share/icons/hicolor/1024x1024/apps/lidar-viewer.png` だけで、hicolor の index.theme には `1024x1024/apps` という場所がない（512x512 まで）。比較: 0.2.0 の deb は 16/32/48/64/128/256 を入れていて、同じ方法で見つかる
- 証拠: 上のスクリプトの出力（報告の「試験の資産」に再実行方法）
- 場所: package.json の build（`linux.icon` の指定なし → build/icon.png（1024）だけが使われた）
- 原因の見立て: 0.3.0 でアイコンを 1024 の 1 枚に作り直した（`gen_icons.py`）ため、electron-builder が 1024x1024 の場所にだけ置いた
- 直し方の案: `build/icons/` に `16x16.png`〜`512x512.png` を置いて `linux.icon: "build/icons"` を指定する（1024 は不要）
- 確度: 再現済み（GTK の探し方で確認。実際のメニュー表示は実機手順 L-2）

### A10-004 [重大] macOS 15 以降: ライブ機能に「ローカルネットワーク」の許可が要るのに、説明文がなく、さらに許可の記録が不安定になる条件（ad-hoc 署名・ほかの Electron アプリと同じ LC_UUID）がそろっている
- 種類: 配布物 / 使い勝手
- 対象: アプリ版（macOS 15 Sequoia 以降、x64・arm64）
- 再現手順: Info.plist を読む／全 Mach-O の LC_UUID を旧版 0.2.0（PCD Viewer）と比べる（`$W/regress/mac_sig_check.py`）
- 期待される結果: `NSLocalNetworkUsageDescription` があり、主の実行ファイルの UUID がこのアプリ固有
- 実際の結果: `NSLocalNetworkUsageDescription` なし。主の実行ファイル「LiDAR Viewer」の LC_UUID は x64 `4C4C44C6-5555-3144-A10F-9FB886F07EF0`・arm64 `4C4C4446-5555-3144-A117-AEB167531362` で、**旧版 PCD Viewer 0.2.0 の主の実行ファイルと完全に同じ**（Electron 34.5.8 の雛形のまま。同じ版の Electron で作ったほかのアプリとも同じになる）。署名は ad-hoc
- 資料（Apple TN3179 Understanding local network privacy）: macOS 15 から、UDP ブロードキャストの送信・ローカルの相手への UDP ユニキャストの送信・UDP ブロードキャストの受信・ローカルの相手への TCP 接続に許可が要る（このアプリでは MID-360 の探索 255.255.255.255:56000、設定の命令、配信の知らせ 47800 の受信、配信元への WebSocket 接続が該当。点群（56301 へのユニキャスト受信）と配信の待ち受けは不要）。「許可の画面を出した直後の操作は、利用者が答える前に拒否されることがある」「ad-hoc 署名だと許可の記録が確実に追えない」「主の実行ファイルの UUID がほかのプログラムと同じだと、おかしな動きをすることがある」。Apple の開発者フォーラムでは、UUID が同じ 2 つのアプリが 1 つの許可の項目を共有し、後のアプリが確認なしに前のアプリの判断を引き継いだ例がある（https://developer.apple.com/forums/thread/766129）。また macOS 27.2 より前は許可を元に戻す方法がない
- 影響: 許可の画面に用途の説明が出ない。拒否された・旧版や別の Electron アプリの判断を引き継いだ場合、MID-360 が「見つからない」だけで理由が分からない（アプリに許可の状態を知らせる表示がない）
- 場所: package.json の `mac`（`extendInfo` なし）、Electron の主の実行ファイル
- 直し方の案: `mac.extendInfo.NSLocalNetworkUsageDescription`（例:「LiDAR（Livox MID-360）を探して点群を受け取り、同じネットワークのほかの LiDAR Viewer と点群をやり取りするために使います。」）。署名前（afterPack）に主の実行ファイルの LC_UUID をアプリ固有の値（appId から作る UUID v5 など）に書き換える。可能なら Developer ID で署名・公証。ライブのカードに「macOS: システム設定 > プライバシーとセキュリティ > ローカルネットワーク で LiDAR Viewer をオンに」という案内を出す
- 確度: 資料による（Apple の技術文書）＋ 配布物の UUID 一致は確認済み。実機の動きは実機手順 M-3

### A10-005 [中] deb の依存の宣言に libgbm1・libasound2（と libdrm2）がなく、最小構成の Ubuntu では入れても起動できない
- 種類: 配布物
- 対象: アプリ版（deb x64・arm64）
- 再現手順: `readelf -d lidar-viewer` で必要なライブラリを調べ、Ubuntu 24.04（noble）の apt の情報で deb の Depends の推移的な閉包に、それぞれの提供パッケージが入るかを `apt-cache depends --recurse` で調べる
- 期待される結果: すべて閉包に入る
- 実際の結果: `libgbm.so.1`（libgbm1）・`libasound.so.2`（libasound2t64）・libdrm2 が閉包に入らない（ほかの NEEDED は libgtk-3-0t64 経由で入る）。普通の Ubuntu Desktop には入っているが、Ubuntu Server（Raspberry Pi 5 のロボットと同じ）に軽い画面環境を足した構成やコンテナでは、`apt install ./LiDARViewer-0.3.0-arm64.deb` が成功しても起動時に `error while loading shared libraries: libgbm.so.1` になる恐れ

- 直し方の案: `deb.depends` に `libgbm1`、`libasound2t64 | libasound2`、`libdrm2` を足す
- 確度: 再現済み（依存の閉包の静的確認）。起動失敗そのものは推定

### A10-006 [中] AppImage が FUSE 2（libfuse.so.2）を必要とする古い型の runtime で、Ubuntu 22.04 以降の既定の状態ではダブルクリックしても起動しない
- 種類: 配布物
- 対象: アプリ版（AppImage x64・arm64）
- 再現手順: AppImage の先頭の ELF（runtime）を調べる（x64: 188,392 バイト、arm64: 197,808 バイト。どちらも動的リンクで `libfuse.so.2` を dlopen する文字列を持つ。squashfs は gzip）
- 実際の結果: Ubuntu 22.04/24.04 は libfuse2 を既定で入れていないため、`dlopen(): error loading libfuse.so.2 … AppImages require FUSE to run.` で止まる（AppImage の既知の動き）。入れた後も 24.04 では A10-001 の理由で落ちる
- 直し方の案: 利用者向け手順に `sudo apt install libfuse2t64`（24.04）/ `libfuse2`（22.04）と `--no-sandbox` を書く。または静的リンクの新しい type2 runtime（libfuse3 内蔵）を使う版の electron-builder に上げる
- 確度: 静的確認 + 公知の動き（実機手順 L-3）

### A10-007 [中] Windows portable: 起動のたびに約 300 MB を一時フォルダへ 2 回書き出す。二重起動すると、動いている方のフォルダを消してから上書きしようとする
- 種類: 性能 / 意図しない挙動
- 対象: アプリ版（Windows portable）
- 再現手順（コード読解）: electron-builder 25.1.8 の `templates/nsis/portable.nsi` と `include/extractAppPackage.nsh`
- 実際の動き: 展開先は `%TEMP%\<ビルドごとの KSUID>`（ビルドのたびに変わる）。起動のたびに (1) `RMDir /r` で展開先を消し、(2) 7z を `$PLUGINSDIR\7z-out` に展開（約 300 MB）、(3) `CopyFiles` で展開先へ写す（さらに約 300 MB）、(4) 終了後にまた消す。2 回目のダブルクリック（1 つ目が動いている間）では、(1) で動いている版の使われていないファイル（ほかの言語の .pak、vk_swiftshader.dll など）を消し、使用中のファイルの上書きに失敗して 1 秒おきに 5 回やり直した後、無音モードのため「再試行」を選んだ扱いで `Nsis7z::Extract` で無理に上書きし、2 つ目のアプリは二重起動として終了、その後 (4) で動いている方のフォルダをまた消す
- 影響: 起動が遅い（ウイルス対策の検査も毎回走る）。二重起動の後、1 つ目は消されたファイル（例: GPU が落ちてソフトウェア描画に切り替わるときの vk_swiftshader.dll）を後で読めず不安定になりうる。前に出るまで 5 秒以上かかる
- 場所: package.json:28-35（`win.target: portable`、`portable.unpackDirName` 未指定）
- 直し方の案: NSIS のインストーラー（`win.target: nsis`、一人用・管理者不要）か zip にする。portable を続けるなら利用者向けに「起動は 1 回だけ。前に出ないときはタスクバーから」と書く
- 確度: コード上の推定（実機手順 W-4 で確認）


### A10-008 [重大] Windows: ライブの受信（UDP 56301・配信の知らせ 47800・配信の待ち受け）が Windows ファイアウォールに止められやすく、止められてもアプリは何も言わない
- 種類: 使い勝手 / 配布物
- 対象: アプリ版（Windows portable）
- 根拠（Microsoft Learn「Windows Firewall rules」）: 受信の許可規則がないアプリが初めて待ち受けると許可を求める画面が出る。「管理者の権限がある利用者が No／取り消しを選ぶと、TCP と UDP の遮断規則が 2 つ作られる」「**管理者でない利用者に画面が出た場合は、どれを選んでも遮断規則が作られる**」
- このアプリでの影響（コード読解: live.js）:
  - 点群は LiDAR の 56300 → PC の 56301 へのユニキャスト。PC から 56301 で何も送っていないので、ステートフルな「返事」として通らず、許可規則がないと遮断される（探索の返事・設定の返事は、こちらから送った直後の返事なので通る）→ **「LiDAR は一覧に出て『表示』も押せるのに、点が 0 点/秒のまま」**になる
  - 配信の知らせ（47800 のブロードキャスト受信）と配信の WebSocket（ランダムな TCP ポートの待ち受け）も遮断され、ほかの PC から配信が見つからない／つながらない
  - 許可の画面の名前は A10-003 のため「Electron」（発行元不明）と出る。portable の展開先は `%TEMP%\<ビルドごとの KSUID>\LiDAR Viewer.exe` で、版を上げるたびに場所が変わるので、許可し直しが要る
  - LiDAR を直結した有線 LAN は「識別されていないネットワーク」＝パブリックになりやすく、許可の画面でプライベートだけにチェックしていると受信できない（実機手順 W-3 で確認）
- 期待される結果: 初回に分かりやすい名前で許可を求め、受信できないときはアプリが原因の候補（ファイアウォール）を知らせる
- 場所: live.js:65-73（bindUdp）、live.js:221（WebSocket.Server port 0）、app.js のライブのカード（受信 0 のときの案内なし）
- 直し方の案: (1) A10-003 を直して許可の画面に「LiDAR Viewer」と出す。(2) NSIS のインストーラー版を用意し、導入時に `netsh advfirewall firewall add rule name="LiDAR Viewer" dir=in action=allow program="…\LiDAR Viewer.exe" profile=any` を入れる（管理者で 1 回）。(3) ライブで「LiDAR につないだのに数秒たっても 0 点/秒」のとき、Windows なら「ファイアウォールで受信が止められている可能性（パブリックのネットワークも許可）」を出す。(4) 利用者向け手順書に許可の手順を書く
- 確度: 資料（Microsoft の文書）とコードによる推定。実機手順 W-3
