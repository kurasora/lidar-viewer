# A03 ファジング（壊れた・悪意のある入力への強さ） 報告

## まとめ

### 試験した範囲
読み込み部品すべて（`src/io/util.js`・`src/io/sink.js`・`src/pcd.js`・`src/trajectory.js`・`src/io/formats/*.js` の
PCD/ASCII/LAS/PLY/E57/PTX/SBF/CloudCompare BIN/PN·PV·SOI·OUT·POLY·SX/OBJ·STL·OFF·VTK·glTF/DXF·SHP·PDMS/画像·GeoTIFF/PSZ）。
Node で読める 55 種の種ファイル（＋手作り）を対象に、**合計 約 5,800 入力**を実行。

### 使った試験技法
- **ファジング（変異）**: ビット反転・バイト置換（0x00/0xFF/0x7F/0x80…）・切り詰め・繰り返し・挿入・削除・数の語の置換・改行/文字コード変換。種を固定し再現可能。
- **ファジング（構造を意識）**: 頭書きの点数/要素数/幅高さを 0／負／2^31-1／2^32-1／1e12／NaN、LZF の usize を巨大に、オフセットをファイル外へ、リストの要素数の嘘、自己参照ブロック、深いネスト。
- **境界値分析・同値分割**（頭書きの数値）、**静的解析**（全読み込み部品のコード読み）、**実際に起こりうる壊れ方**（途中切れ＝ROS 記録停止・コピー切れ、CRLF/CR/BOM/UTF-16、文字コード）。
- 実行器は「1 プロセスで多数を回し、子プロセスごとに時間（既定 15〜20 秒）と RSS（450 MB で停止）を測る」形（`$W/fuzz/runner.mjs`）。

### 見つけた数: 致命 2 / 重大 1 / 中 4 / 軽微 1 / 情報 1（＋ 担当外 1）

### 結果の全体像
- **プロセスが落ちた（segfault 等）: 0 件**（堅牢。すべて JS 例外として捕まる）。
- **固まった（時間切れ）: 1 件**、**メモリ上限で停止: 8 件**（いずれも「頭書きの数を無制限に信用」→ 過大確保・充填。致命 A03-001）。
- **内部の英語例外がそのまま出る: 約 20 箇所・延べ 700 件超**（重大 A03-003）。
- **黙って非有限座標を表示: 約 110 件**（致命 A03-002）。

### 問題なかったこと（確認できて OK）
- **55 種の正常な種ファイルはすべて正しく読めた**（点数・平均・最小/最大が期待値どおり。`$W/out/base.jsonl`）。
- **失敗のあとの回復は OK**（ブラウザ version で確認）: VTK/OFF/PLY/DXF/PDMS の各エラーの直後に正常な PCD を開くと、普通に n=5000 で開けた。順番待ちが止まったり「開いています」が残ることはなかった（`$W/out/browser.jsonl`）。
- **手書きのテキスト系読み取り（ASCII 点群・PN/PV/SOI/OUT/POLY/SX・PCD ヘッダ・CloudCompare BIN v1/v2）は、壊れた入力でもほぼ全て日本語の誤り**を返した（`BIN ファイルが途中で切れているか、壊れています` 等）。再帰で木をたどる CloudCompare BIN v2 でも、`need()` の範囲検査が効いてプロセスは落ちない。
- **LZF の参照範囲外・圧縮データ破損**は専用の日本語エラー（`圧縮データが壊れています`）で正しく弾く。`new Uint8Array(usize)` は Node では遅延確保のため小入力でも RAM を食わなかった（→ 情報 A03-009 に整理）。
- **E57・PCD binary の本体途中切れ**は日本語の `…が途中で切れています`。**CRLF・BOM（PLY 以外）・LF/CRLF 混在**はおおむね正しく読めた。
- 二重の NaN/Inf トークン（"nan"/"inf"/1e400）は `sink.slot` と `parseToken` で正しく除外される（※ただし float32 の範囲は別問題＝A03-002）。

## 見つけた問題

### A03-001 [致命] 頭書きの点数・寸法を無制限に信用し、小さなファイルで数 GB を確保・充填してフリーズ/OOM
- 種類: バグ / セキュリティ（DoS）
- 対象: アプリ version・試作ページの両方（読み込みは別スレッド `worker.js`。同じコード）
- 再現手順:
  - `$W/crashers/vtk_fill_3e8.vtk`（81 バイト。`POINTS 300000000 float` と書いただけ）を開く。
  - `$W/crashers/pgm_mid_20k.pgm`（19 バイト。`P5 20000 20000 255`）を開く。
  - 他に OFF の頂点数（`$W/crashers/off_nv_1e9.off`）、PPM/XPM/TGA/WBMP の幅×高さ、変異で壊れた OFF（`$W/crashers/off_havoc_oom.off`）、TGA（`$W/crashers/tga_havoc_hang.tga`）。
- 期待される結果: ファイルの実データ量に見合わない点数・寸法は拒否するか、実際に読めた分で止める。小さなファイルで GB 単位を確保しない。
- 実際の結果: VTK は `new Float64Array(POINTS*3)`（mesh.js:155）、OFF は `new Float64Array(nv*3)`（mesh.js:126）、画像は `new Uint8ClampedArray(w*h*4)`（image.js:37/57/88）を**頭書きの数そのままで確保**し、ASCII の読み出しループが末尾超過でも `0` を書き続けて**全域をゼロ埋め**する。試験では `POINTS 3e8`（7.2 GB 相当）・`20000×20000`（1.6 GB）で RSS が上限（450/600 MB）に達して停止（15〜18 秒で増加中）。2 CPU・7 GB の実機では**タブ（レンダラ）が OOM で落ち、進捗は「開いています」のまま**になる。
- 証拠: `$W/out/struct.jsonl`（`vtk_points_3e8`=mem, `off_nv_1e9`=Range'Array buffer allocation failed'）、`$W/out/tprobe.jsonl`（`pgm_mid_20k`・`vtk_ascii_fill_1e8`=mem 16〜18s）、`$W/out/havoc.jsonl`（`cc_mesh.off#7/#15/#24`=mem、`pillow_topview.tga#13`=hang、`pgm/ppm#31`=mem）。
- 場所: `src/io/formats/mesh.js:126`（OFF `new Float64Array(nv*3)`）, `mesh.js:155`（VTK `arr`）, `src/io/formats/image.js:10,37,57,88`（`addPixels`/`pnm`/`tga`/`xpm`）, `src/io/formats/ply.js:66`（`new Float64Array(vEl.count*3)`）。
- 原因の見立て: 頭書きの数（points/nv/width×height/vertex count）を、ファイルの残りサイズと照らさずにそのまま確保・反復している。`sink` 経由（cap で頭打ち）なら守られるが、これらは `sink` を通さず直接確保する。
- 直し方の案: 確保する要素数を「残りのファイルサイズ ÷ 1 要素の最小バイト数」で上限する（例: OFF/VTK の ascii は行数、画像は w·h を `src.size` と突き合わせる）。`sink.hint` と同様に `cap` も尊重する。ascii の `arr()` は読み出し語が尽きたら打ち切る。
- 確度: 再現済み（Node。worker.js と同一コード）
- 再現スクリプト: `$W/regress/checks.sh`（`vtk_fill_3e8` `pgm_mid_20k` `off_nv_1e9` `off_havoc_oom`）

### A03-002 [致命] 座標が float32 の範囲を超えると黙って Infinity になり、点群が壊れて表示される（「開きました」と出る）
- 種類: バグ / 意図しない挙動（黙ってデータが間違う・表示が壊れる）
- 対象: 両方
- 再現手順:
  1. `$W/crashers/float32_overflow.xyz`（`1 2 3` / `4 5 1e39` / `7 8 9` の 3 行）を開く → 2 点目の z が Infinity になる。
  2. `$W/crashers/offset_poison.xyz`（先頭が `1e300 1e300 1e300`、以降は普通の小さな座標）を開く → **先頭以外の全点が -Infinity**（グローバルシフト汚染）。
- 期待される結果: float で表せない座標は除外し（`skipped` に数え）、知らせに警告を出す。巨大な外れ値 1 点で全体が壊れない。
- 実際の結果: `sink.slot` の番兵は `isFinite()` を **double** で検査するが、座標は **Float32Array**（`this.P`）に格納される（sink.js:70）。`3.4e38 < |v| < 1.8e308` の有限 double は番兵を通り抜け、格納時に ±Infinity に化ける。さらに `this.offset` は**最初に受理した 1 点**から決まる（sink.js:54）ため、先頭が巨大だと `x - offset` が全点で桁あふれして ±Infinity になる。読み取りは `n` と書式を返して**成功扱い**。結果の `positions` に Infinity が入り、worker の `bbox`（worker.js:77、非有限を除外しない）と three.js の境界球が Infinity になって、**画面の枠決め・描画が壊れる**。知らせは通常の成功メッセージ。
- 実測: `float32_overflow.xyz` → n=3・`max=[7,8,Infinity]`。`offset_poison.xyz` → n=4・12 個中 9 個が -Infinity。変異ファジングでも asc/csv/xyz/ply/obj/off/vtk/soi/poly/sx/pcd/stl/**shp/dxf/las** など広く非有限が発生（延べ約 110 件。`$W/out/*.jsonl` の `NONFINITE`、`pyshp_lines.shp#0` は 299,954 点中 586,408 値が非有限、bbox 全軸 ±Infinity）。
- 証拠: `$W/fuzz/debug_nf.mjs` の出力、`$W/out/{havoc,token,head}.jsonl`、**ブラウザ version（dist）での確認 `$W/out/browser.jsonl`**: `float32_overflow.xyz` を開くと n=3・`max=[7,8,Infinity]` で読み込みは成功扱いになり、ページに `THREE.BufferGeometry.computeBoundingSphere(): Computed radius is NaN. The "position" attribute is likely to have NaN values` が出た（＝境界球が NaN＝枠決め・カリングが壊れる）。知らせはこのデータ異常を伝えない。
- 場所: `src/io/sink.js:52-54,70`（`slot` の番兵と Float32 格納・offset 決定）、`src/worker.js:77-83`（bbox が非有限を除外しない）。
- 原因の見立て: 有限性の検査が格納型（float32）と一致していない。offset を 1 点だけで決め、妥当範囲の検査がない。
- 直し方の案: `slot` で `Math.fround(v)` が有限かも確認して弾く（または z を double 保持）。offset は最初の数十点の中央値や bbox から決め、巨大外れ値 1 点に引きずられないようにする。`bbox`・`finish` で非有限を除外し、除外数を知らせに出す。
- 確度: 再現済み（Node ＋ **ブラウザ version**。positions に Infinity が入り、three.js の境界球が NaN になることを確認）。
- 再現スクリプト: `$W/regress/checks.sh`（`float32_overflow`）＋ `$W/crashers/offset_poison.xyz`

### A03-003 [重大] 壊れた・途中で切れた入力で、内部の英語例外がそのままユーザーに出る
- 種類: バグ / 文言（誤りの知らせが日本語でなく、内部メッセージ・型名がそのまま）
- 対象: 両方
- 再現手順（例。いずれも `status('エラー: ' + message, true)`＝赤字でそのまま表示される）:
  - 途中で切れた binary PLY（`$W/crashers/ply_binary_truncated.ply`）→ `Offset is outside the bounds of the DataView`
  - 途中で切れた OFF（`$W/crashers/off_truncated.off`）→ `Cannot read properties of undefined (reading 'split')`
  - 途中で切れた glTF/GLB → `Unexpected end of JSON input` / `Unterminated string in JSON…` / `Invalid character`（atob）
  - LAS のヘッダ途中切れ（4/128 バイト）→ `Offset is outside the bounds of the DataView`
  - 壊れた XBM/XPM → `Cannot read properties of null (reading '1')` / `…(reading 'trim')`
  - 壊れた GeoTIFF → `Invalid byte order value.` / `Invalid field type: N`（geotiff ライブラリ）
  - 壊れた PSZ → `invalid zip data` / `unknown compression type N` / `invalid distance`（fflate ライブラリ）
  - 壊れた PCD binary の TYPE → `rd[iy] is not a function`
- 期待される結果: どの形式でも「このファイルは壊れている/途中で切れているため開けません」等の**日本語**の知らせ。内部の型名・英語・stack を出さない。
- 実際の結果: 約 20 箇所から `RangeError`/`TypeError`/`SyntaxError`/`DOMException` がそのまま漏れる。これは ROS 記録の途中停止・コピー途中切れ・文字コード違いなど**普通に起こる壊れ方**で発生する（全切り詰め試験 1,331 件中 256 件が英語例外。`$W/out/trunc.jsonl`）。`worker.js:466` の文言書き換えは WebAssembly/CSP 関連しか拾わないため、これらは素通りする。
- 証拠: `$W/out/{trunc,havoc,head}.jsonl`、集計は `$W/regress/summarize.mjs`（「英語/内部例外が漏れる箇所」）。**ブラウザ version（dist）で赤字表示を確認（`$W/out/browser.jsonl`）**: `vtk_points_1e9.vtk`→「エラー: Array buffer allocation failed」、`off_truncated.off`→「エラー: Cannot read properties of undefined (reading 'split')」、`ply_binary_truncated.ply`→「エラー: Offset is outside the bounds of the DataView」。これらエラーの**後に正常ファイルを開くと普通に開けた（回復は OK）**。
- 場所（代表）: `ply.js:127/130/132`, `mesh.js:78(STL)/121-129(OFF)/155-159(VTK)/246-270(glTF)`, `cad.js:143-165(SHP)`, `las.js:15-18`, `e57.js:18/92/137`, `image.js:37/57/61/70/79/83/88/138/163`, `pcd.js:37/77/79`, `psz.js:8`。
- 原因の見立て: バイナリは `DataView`/`new Uint8Array(n)` を範囲検査なしで使い、JSON は `JSON.parse` を try で包んでいない。外部ライブラリ（geotiff・fflate・laz-perf）の英語例外もそのまま。
- 直し方の案: 各読み取りの入口を try で包み、`DataView`/型付き配列の `RangeError`・`JSON.parse` の `SyntaxError`・ライブラリ例外を「このファイルは壊れている可能性があります（<形式>）」の日本語に正規化する（`worker.js` の最終 catch に、既知パターン→日本語の対応表を足すのが最小改修）。
- 確度: 再現済み（Node ＋ **ブラウザ version**）。表示経路は `app.js:46`（`status('エラー: ' + m.message, true)`）。
- 再現スクリプト: `$W/regress/run.sh`（trunc キャンペーン）＋ `$W/regress/checks.sh`

### A03-004 [中] 自己参照する DXF ブロック・深い PDMS ネストで無限再帰（スタックオーバーフロー）
- 種類: バグ（DoS）
- 対象: 両方
- 再現手順: `$W/crashers/dxf_self_insert.dxf`（ブロック A が INSERT A）、`$W/crashers/dxf_mutual_insert.dxf`（A→B→A）、`$W/crashers/pdms_deep_new.pdms`（`NEW` を 6 万回ネスト）。
- 期待される結果: 参照の循環・深さに上限を設け、日本語で知らせる。
- 実際の結果: いずれも `Maximum call stack size exceeded`（英語）。DXF は `emit`→INSERT→`emit`（cad.js:97）が循環参照で無限再帰。PDMS は `walk`→`walk`（cad.js:259）が深いネストで溢れる。プロセスは落ちないが A03-003 と同じく英語で出る。
- 場所: `src/io/formats/cad.js:54-100`（`emit`、INSERT）、`cad.js:243-260`（`walk`）。
- 原因の見立て: 再帰に訪問済み集合・深さ制限がない。
- 直し方の案: `emit` に展開済みブロック名のスタックを渡して循環を検出、`walk` に深さ上限（例 1000）。超えたら日本語で知らせる。
- 確度: 再現済み（Node ＋ **ブラウザ version**。3 例とも「エラー: Maximum call stack size exceeded」が赤字表示、`$W/out/browser.jsonl`）
- 再現スクリプト: `$W/regress/checks.sh`（`dxf_self_insert` `dxf_mutual_insert` `pdms_deep_new`）

### A03-005 [中] CR のみの改行（旧 Mac 形式）だと全テキスト形式が開けない
- 種類: バグ（互換性）/ 意図しない挙動
- 対象: 両方
- 再現手順: `$W/crashers/cr_only.pcd`（正常な `pcl_ascii.pcd` の `\n` を `\r` に置換）を開く。ASCII/XYZ/PLY(ascii)/OBJ/VTK でも同様。
- 期待される結果: CR 改行の有効なファイルも開ける（CloudCompare は開ける）。
- 実際の結果: `eachLine`（util.js:107）は 0x0A のみで行を切り、`\r` では切らない。`ascii.js:22` の `split(/\r?\n/)` も同様。CR のみのファイルは全体が 1 行とみなされ、PCD は `PCD のヘッダーが読めません（DATA 行が見つからない）`、ASCII/XYZ は `数値の行が見つかりません`、PLY は `PLY のヘッダーが読めません`、OBJ は `頂点（v）がありません`、VTK は `VTK に点（POINTS）がありません` で失敗。
- 証拠: `$W/fuzz/cr_probe.mjs` の出力（LF/CRLF/BOM は OK、CR のみ全滅）、`$W/out/nl.jsonl`。
- 場所: `src/io/util.js:100-120`（`eachLine`）、`src/io/formats/ascii.js:22`、`src/io/formats/mesh.js`（OFF/STL/OBJ の `split(/\r?\n/)`）。
- 原因の見立て: 行の区切りに 0x0D（単独 CR）を含めていない。
- 直し方の案: `eachLine` で 0x0D も行末として扱う（0x0D の次が 0x0A ならまとめて 1 改行）。`split(/\r?\n/)` を `split(/\r\n|\r|\n/)` に。
- 確度: 再現済み
- 再現スクリプト: `$W/fuzz/cr_probe.mjs`

### A03-006 [中] SBF の値の欄数を 65535 にすると O(n²) で約 14 秒フリーズ
- 種類: 性能（DoS）
- 対象: 両方
- 再現手順: `$W/gen/files/struct/sbf_nsf_65535/`（`.sbf` に `SFCount=65535`、`.sbf.data` の欄数も 0xFFFF）。
- 期待される結果: 欄数が多くても速やかに読むか、妥当な上限で断る。
- 実際の結果: 約 13.9 秒かかる（`$W/out/struct.jsonl` の `sbf_nsf_65535`=SLOW）。`sink.field(name)`（sink.js:27）が毎回 `names.indexOf` の線形探索をするため、欄を 65535 個作る処理が O(n²)≈21 億回になる。SBF 以外でも、欄名が多い形式（CloudCompare BIN・E57・PLY）で欄数が大きいと同様に効く。
- 場所: `src/io/sink.js:26-33`（`field`）、`src/io/formats/sbf.js:63-67`。
- 原因の見立て: フィールド名→番号の対応に線形探索を使っている。
- 直し方の案: `sink` に `Map<name, index>` を持たせて `field` を O(1) に。SBF は欄数に妥当な上限（例 4096）。
- 確度: 再現済み
- 再現スクリプト: `$W/gen/struct.mjs` で生成 → `runner.mjs`

### A03-008 [情報] 過大な宣言値で最大 4 GB 級の仮想確保を試みる（Node では遅延確保のため実害小）
- 種類: 情報（確認したい）
- 対象: 両方（主にブラウザのワーカーで影響を確かめたい）
- 内容: PCD binary_compressed の `usize`（pcd.js:38 `new Uint8Array(usize)`）、E57 の `xmlLen`（e57.js:18）、OFF/VTK の `nv*3` などは、頭書きの uint32/uint64 をそのまま確保する。Node では遅延確保のため小入力では RSS が増えず、`new Uint8Array(0xFFFFFFF0)`（約 4 GB）も即座には実害がなかった（その後 `圧縮データが壊れています` 等で弾かれる）。ただしブラウザの別スレッド（アドレス空間が狭い／`OffscreenCanvas` 併用時）では `RangeError` や確保失敗になりうる。A03-001 と合わせ、宣言値をファイルサイズで上限するのが根本対策。
- 確度: Node で確認（遅延確保のため小入力では無害）／ブラウザは未確認。

### A03-009 [軽微]（担当外・A08/水平補正の範囲）正常なファイルを開いただけで赤字の「水平補正できませんでした」が出る

- 対象: 両方

### 環境のはまりどころ・コツ
- 巨大な型付き配列は **ArrayBuffer（ヒープ外）**で、Node の `--max-old-space-size` では止まらない。メモリ爆発は RSS を監視して止める必要がある（runner.mjs がそうしている）。また Node の確保は**遅延**のため、`new Float64Array(巨大)` 自体は RSS に出ず、ゼロ埋め（書き込み）で初めて増える。
- `guard`（light/heavy）は子孫 RSS の合計で止める。runner の `--mem` を guard の上限より十分低くしておくと、guard に巻き込まれず 1 件ずつ評価できる。
- 子を 1 つ使い回すと速いが、固まる/メモリ爆発の入力は子を強制終了して次の子を起こす（runner.mjs 実装済み）。
