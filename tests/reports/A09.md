### 測るもの
1. 大きな点群の読み込み: 形式（PCD binary / binary_compressed / ascii、LAS、LAZ、PLY binary、E57、XYZ 文字）× 点数（1,000 万・3,000 万・5,000 万）
   - 時間: 読み込み（読み取り）・並べ替え・画面に出るまで・索引（点の間隔）まで。速度（MB/秒・点/秒）
   - メモリ: 画面（レンダラ）・GPU・主プロセスの各プロセスの最大 RSS／PSS（/proc を 0.2 秒ごとに見る）。JS ヒープ（CDP の Runtime.getHeapUsage、画面とワーカー別）
   - 進み具合の表示が単調に進むか（幅・文言の列を記録）、画面が固まる時間（長いタスク・requestAnimationFrame の間隔）
2. 上限: 上限より多い点（5,000 万点を上限 1,000 万・3,000 万で）→ 間引きの時間と結果（平均・範囲が全体と一致するか＝偏りがないか）。上限 1 億・10 億 → メモリの足りない状況（RLIMIT_DATA で確保の失敗を起こす＝Windows に近い／guard の上限＝OOM に近い）での知らせ
3. リーク: 同じ大きめのファイル（1,000 万点）を 20 回開いて閉じる、200 個の小さなファイル、色（値⇔高さ）・計測の切り替えの繰り返し → JS ヒープと RSS と GPU プロセスが元に戻るか
4. 読み込み中の操作: 別のファイルを閉じる・開く、視点を動かす、上限を変える
5. LOD の効果（ドラッグ中とホイール中のフレーム時間の比較）、待機中の CPU 使用率
6. Electron 版で主要なもの（3,000 万点 LAS／PCD、リーク）と、`app.getAppMetrics()` によるプロセス別メモリ
7. 仮説 H4 の確認（疎で広い点群 2,000 万点、上限 3,000 万）

### 使う技法
負荷試験・耐久（繰り返し）試験・境界値分析（上限ちょうど・上限＋1、Map の 2^24）・状態遷移（読み込み中の操作）・静的解析（ソースからの仮説）・故障注入（RLIMIT_DATA でメモリ確保を失敗させる）

### 優先順位
H4（落ちる・取り違え）→ H5/H6（メモリ不足時の挙動）→ 1（表）→ 3（リーク）→ H10/LOD → その他

### A09-001 [重大] たくさんのファイルを開く・閉じると、1 つごとに画面が数秒固まり、全体の時間がファイル数の 2 乗で延びる（50 個で 81 秒、200 個では推定 20 分以上）
- 種類: 性能
- 対象: 両方（アプリ版・試作ページ。画面側の処理）
- 再現手順:
  1. 2 万点の PCD（LiDAR の 1 フレーム相当）を 50 個用意する（`python3 $W/regress/gen_frames.py --count 200 --n 20000 --out DIR`）
  2. ファイルを開く画面で 50 個をまとめて選ぶ（`node $W/regress/many_files.js DIR 50`）
  3. 全部開いたら、一覧の × で 1 つずつ閉じる
- 期待される結果: 1 ファイルあたりの時間がほぼ一定（合計 100 万点なので、1 つの 100 万点ファイルと同じくらいの時間）で、画面が固まらない
- 実際の結果（Chromium 141、2 CPU）:
  - 50 個を開き終わるまで **81.2 秒**。1 つ開くごとの間隔が、最初の 10 個は平均 0.55 秒 → 最後の 10 個は平均 **2.85 秒**（後になるほど遅い）
  - その間、画面（メインスレッド）は **合計 79.4 秒** 長いタスクで固まっていた（最長 3.3 秒。0.5 秒以上フレームが止まった回数 67）
  - 50 個を 1 つずつ閉じるのに **61.4 秒**（1 回 1.2 秒）。「すべて閉じる」ボタンはない
  - 同じ計算を Node で再現（`sim_bounds.mjs`）すると、ファイル 1 つを開く・閉じるたびの計算が 50 個で 3.8 秒、100 個で 9.3 秒、200 個で **29 秒**。200 個を順に開くと合計 20 分以上かかる見込み
- 証拠: `$W/out/b1.jsonl`（`"test":"many_files"` の行）、`$W/out/prof_c2M_las.json`（1 ファイルでも updateBounds が 1 回 0.5〜1 秒）
- 場所: src/app.js:312-336（updateBounds）、:320、:348-356（updateCeiling）、:383-388（visibleZ）、:698（onLoaded から毎回）、:776（閉じるたびに毎回）、:1438（水平補正のたび）
- 原因の見立て: `updateBounds` が、表示中の**全ファイル**から標本（`Math.max(50000, 400000 / ファイル数)` 点ずつ）を取り直し、3 軸それぞれを JS の配列に push して比較関数つきで `sort` し、さらに `updateCeiling` が高さを集め直してもう一度 `sort` する。コメントの意図は「全体で 40 万点」だが、`Math.max(50000, …)` のため 9 個目以降は 1 ファイル 5 万点（またはそのファイルの全点）ずつ増え続け、標本の総数がファイル数に比例 → 1 回の計算が O(N log N)、それを開く・閉じるたびに全ファイル分やり直すので合計は O(ファイル数² log)
- 直し方の案: ①標本の総数を本当に 40 万点に抑える（`Math.floor(400000 / vis.length)`、下限は小さく）②ファイルごとの標本を `f` に持っておき、変わったファイルだけ作り直す ③並べ替えは Float32Array の `sort()`（比較関数なしの数値並べ替え）か、ヒストグラム（分位点は 1024 区間程度で十分）で置き換える ④順番待ちにまだファイルがあるときは `updateBounds`・`applyColor`・`renderFileList` を最後の 1 回だけにする ⑤「すべて閉じる」ボタン
- 確度: 再現済み（50 個）／200 個は計算の再現からの見積もり（実測は追記予定）
- 再現スクリプト: `$W/regress/many_files.js`、`$W/regress/sim_bounds.mjs`、`$W/regress/gen_frames.py`

### A09-002 [中] LAZ を一度開くと、閉じたあともファイルの大きさ分のメモリ（wasm のメモリ）が別スレッドに残り続ける
- 種類: 性能（メモリが戻らない）
- 対象: 両方
- 再現手順: 1,000 万点の LAZ（94 MB）を開いて閉じる、を 5 回（`node $W/regress/scenarios.js reopen --k=5 <c10M.laz>`）。閉じたあと GC して、別スレッドの ArrayBuffer（CDP の Runtime.getHeapUsage の backingStorageSize）を見る
- 期待される結果: 閉じたら起動直後（16 MB）に戻る（PCD・LAS では戻る）
- 実際の結果: 閉じたあとも **130 MB**（+114 MB ≒ ファイルの大きさ＋展開用の領域）のまま。5 回とも同じ（増え続けはしないが、いちばん大きかった LAZ の分がずっと残る）。画面のプロセスの RSS も 542 MB（PCD を閉じた後は 410 MB）。大きいほど多く残る:
  | LAZ | 大きさ | 閉じたあとの別スレッドの ArrayBuffer |
  |---|---|---|
  | 200 万点 | 19 MB | 44 MB（+28） |
  | 1,000 万点 | 94 MB | 130 MB（+114） |
  | 3,000 万点 | 282 MB | 356 MB（+340） |
  | 5,000 万点（上限 3,000 万で間引き） | 471 MB | **582 MB（+566）** |
- 証拠: `$W/out/b2.jsonl`（`"scenario:reopen"` の `c10M.laz` 行。`wAB` が 130）、`$W/out/b1.jsonl`・`b3.jsonl`・`b4.jsonl`（LAZ の行の `afterClose.heap.worker.ab`）
- 場所: src/io/formats/las.js:5-9（`lazModule` を作ったら使い回す）、:86-118（`L._malloc(src.size)` でファイル全体を wasm のメモリに写す）
- 原因の見立て: laz-perf（Emscripten）の wasm のメモリは一度広がると縮まない。展開部品（`lazModule`）を別スレッドの間ずっと使い回すので、それまでに開いた最大の LAZ の大きさ分が、アプリを閉じるまで戻らない。1.5 GB の LAZ を一度開くと 1.5 GB 以上が残る
- 直し方の案: ①ファイルごとに `createLazPerf()` で作り直し、終わったら参照を捨てる（wasm のメモリごと GC される）②ファイル全体を写さず、laz-perf の ChunkDecoder などでチャンクごとに展開する（1.8 GB の上限もなくなる）③ wasm の部品はアプリ版ではワーカーに埋め込まず、使うときだけ読む
- 確度: 再現済み（200 万〜5,000 万点）
- 再現スクリプト: `$W/regress/scenarios.js reopen`、`$W/regress/perf_load.js --close`

### A09-003 [重大] 広い範囲の疎な点群（2,500 万点）を開くと、表示されたあとに「エラー: Map maximum size exceeded」と赤く出て、点の間隔・点の選択（座標・距離）が使えない
- 種類: バグ
- 対象: 両方
- 再現手順:
  1. 15 km 四方の地形に 2,500 万点（空からの LiDAR を間引いたような密度 0.11 点/m²、UTM 座標）の LAS を作る: `python3 $W/regress/gen_big.py --n 25000000 --kind sparse --out DIR --formats las --name sparse_25M`
  2. 既定の上限（3,000 万点）のまま開く（`node $W/regress/perf_load.js --stats DIR/sparse_25M.las`）
- 期待される結果: 開けて、点の間隔が出て、点をクリックすると座標が出る
- 実際の結果: 点群は表示される（「sparse_25M.las を開きました（25,000,000 点）」）が、その **13 秒後**に `エラー: Map maximum size exceeded`（赤、英語のまま）。情報の「点の間隔」はずっと「計算中…」。点の選択（座標・距離）も同じ索引を作り直すので毎回失敗する。続けて水平補正も「平面が少なすぎて…」で失敗（こちらは地形なので妥当）
- 証拠: `$W/out/b2.jsonl`（`sparse_25M.las` の行。`workerErrors: [[26561, 1, "Map maximum size exceeded"]]`）
- 場所: src/worker.js:86-112（buildIndex）、:91（`cell = min(2, …)`）、:94-103（`ids = new Map()` にセルごとに 1 件）、:433（読み込み直後に pointSpacing）
- 原因の見立て: 点の選択・点の間隔の索引は、空でない格子のセルを JS の `Map` に入れる。セルの大きさは最大 2 m に制限されているので、広くて疎な点群ではほぼ 1 点 = 1 セルになり、V8 の Map の上限（2^24 = 16,777,216 件）を超える。上限 1 億・10 億にして空からの LiDAR（数 km 四方）を開くと、もっと起きやすい。さらに 2^24 件近くまで Map に入れるのに 14 秒かかり、その間は別スレッドがふさがる
- 直し方の案: Map をやめて、セル番号（整数）を `Float64Array`/`Uint32Array` に入れて並べ替え（基数ソート）し、二分探索で引く。または、セルの大きさの上限 2 m をなくし、点の数 ÷ 8 程度のセル数になるよう決める。索引づくりの失敗は「読み込みの失敗」と区別し、分かる日本語で知らせる（点の選択だけ使えない、など）
- 確度: 再現済み
- 再現スクリプト: `$W/regress/gen_big.py --kind sparse`、`$W/regress/perf_load.js`

### A09-005 [中] 操作中の間引き（LOD）がホイールのズーム・視点ボタンのアニメーション・中心の印のドラッグでは効かず、毎回全点を描く（1,000 万点でドラッグの 6.5 倍遅い）
- 種類: 性能
- 対象: 両方
- 再現手順: 1,000 万点の LAS を開き（「操作中の点数」は既定の 150 万点）、①左ドラッグで回す ②ホイールでズーム ③視点のボタン ④中心の印をドラッグ、を行い、描画 1 回ごとの描いた点数と時間を記録（`node $W/regress/lod.js <c10M.las>`。描画のあと readPixels で描き終わりを待って測る）
- 期待される結果: どの操作中も 150 万点に間引かれる
- 実際の結果（SwiftShader なので絶対値は実機と違う。比を見る）:
  | 操作 | 描いた点数 | 1 回の描画 |
  |---|---|---|
  | 左ドラッグ（回転） | 150 万（間引きあり） | 0.68 秒 |
  | ホイールでズーム | **1,000 万（全点）** | 4.46 秒 |
  | 視点ボタン（0.42 秒のアニメーション） | **1,000 万** | 4.85 秒（アニメーションが 1 コマになる） |
  | 中心の印のドラッグ | **1,000 万** | 4.83 秒（＋1 回ごとに点の選択） |
  直接測ると、全点 4.94 秒・50% 2.38 秒・15% 0.68 秒・5% 0.23 秒（点数に比例）。30 回のホイールに 135 秒、ドラッグ 30 回は 39 秒
- 証拠: `$W/out/b2.jsonl`（`"test":"lod"`）
