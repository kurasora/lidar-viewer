### 問題なかったこと（確認して OK だった項目）
- UDP の受信（live.js `onPoints` `onDetect` `onCmd` `parseCmd`）は長さと範囲を確かめてから読んでおり、短い/壊れたパケットでは落ちない。`bindUdp` は socket の `error` を拾う。`PeerFinder` のビーコンは `JSON.parse` を try/catch で囲む。ポートが 0・巨大・なしのビーコンも一覧に出ない/つなげずに握る（crash しない）。
- 配信の WebSocket の接続失敗（相手がいない・拒否）は `ws.on('error')` で拾い、主プロセスは落ちない（落ちるのは**メッセージ本文**の経路のみ。A12-001）。
- `ipcMain.handle` は `live:open` で `Live` を遅延生成。ふつうの操作順（カードを開く＝open → 一覧 → 表示）では null 参照にならない。
- `requestSingleInstanceLock` による二重起動の防止は機能（`second-instance` で既存窓を前面化）。`PCDV_USERDATA` の切り替えも機能。
- ファイルを閉じると `geom.dispose()` `mat.dispose()` を呼び、ワーカーにも `remove` を送る。点群が全部なくなったときに情報・計測・水平補正・天井の状態を消す処理（的外れな知らせの抑制。README の過去要望）も入っている。
- 読み込みの順番待ち（queue/loading）はワーカーが 1 メッセージずつ処理するため、同時に 2 件読み込むことはない。ファイル ID は `++S.seq`、リクエスト ID は `++reqSeq` で単調増加し、取り違えは起きない。
- `title` 属性を消す MutationObserver（マウス吹き出しを出さない要望）、座標の球が常に見える（`depthTest:false` `frustumCulled:false`）、座標と距離の排他（`setTool`）、カードの重なり・詰め（popStack）は実装どおり。
- CSP に `script-src 'unsafe-inline'` が無いため、未エスケープの項目名に含めた `onerror=` などの**インラインのコードは実行されない**（A12-012 は DOM/HTML 注入に留まる）。
- eslint recommended では致命的な誤り 0（警告 2 = 未使用変数のみ）。

### A12-001 [致命] 配信を受けると、壊れた WebSocket メッセージ 1 通で主プロセスが落ちる
- 種類: バグ / セキュリティ（ネットワーク起点の DoS）
- 対象: アプリ version（全 OS）。試作ページは配信を受けないので対象外
- 再現手順: 同じ LAN の別ホストが UDP 47800 に `{app:'pcd-viewer', port:…}` を流して「配信元」として一覧に出し、利用者がそれを「表示」で選ぶ（`startPeer`）。その WebSocket 接続に対し、本文が `"PCV1" + 点数(uint32)` だけで点数を巨大（例 0x7fffffff）にした、または点数に対して本文が短いメッセージを送る。
  - 再現スクリプト: `$W/regress/live/run_decode_crash.sh`（netns a121=受け手、a122=壊れた配信元）。
- 期待される結果: 壊れたメッセージは無視して表示を続ける（最悪でもその配信だけ止める）。
- 実際の結果: 主プロセスが `RangeError: Invalid typed array length: 6442450941`（`live.js:213` `decodeBatch`）で終了。Node での被害側の終了コードは 1。Electron では未捕捉例外となり「A JavaScript error occurred in the main process」で落ちる（主プロセスなので窓ごと終了）。
- 証拠: `$W/regress/out/victim.log`（スタックトレース）、`$W/regress/out/badpeer.log`。
- 場所: `live.js:209-214`（`decodeBatch`）、呼び出しは `live.js:311`（`ws.on('message', d => { const b = decodeBatch(d); … })`）。`main.js` に `process.on('uncaughtException')` は無い（確認済み）。
- 原因の見立て: `decodeBatch` が本文から読んだ点数 `n` を検査せず `new Float32Array(copy.buffer, copy.byteOffset + 8, 3 * n)` に渡す。`n` が巨大、または本文長が `8 + 13*n` に満たないと TypedArray 構築が投げる。`message` ハンドラに try/catch が無く、主プロセスに未捕捉例外ハンドラも無いため落ちる。
- 直し方の案: `decodeBatch` で `if (n < 0 || 8 + 13 * n > buf.length) return null;` を先に入れる。あわせて `ws.on('message')` のコールバックを try/catch で囲む（壊れた本文は捨てる）。保険として `main.js` に `process.on('uncaughtException')` を置き、ライブ関連の例外ではログに留めてアプリは落とさない。
- 確度: 再現済み（Node。`live.js` は主プロセスのコードそのものなので Electron でも同じ経路）。
- 再現スクリプト: `$W/regress/live/run_decode_crash.sh`（`victim.js` `badpeer.js`）

### A12-005 [中] GeoTIFF の float の nodata が `===` で外れず、1 点が極端な高さになり z が壊れる
- 種類: バグ（点群が黙って間違う）
- 対象: 両方（ラスター/GeoTIFF の高さ表示）
- 再現手順: 1 バンドの float32 DEM で GDAL_NODATA を丸めた文字列（例 `-3.40282e+38`）で書いたものを開く → `$W/regress/data/dem_nodata.tif`。
- 期待される結果: nodata のマスを除外し、有効値（例 10〜20 m）だけで表示・色付けする。
- 実際の結果: nodata が除外されず、該当マスが z=-3.40282e+38 の点になる。高さの範囲・色・視点合わせがすべて壊れる（除外 0 と表示）。
- 証拠: `$W/regress/out/readers.txt`（A12-tif-nodata: 最小の高さ -3.4e38、除外 0）。
- 場所: `src/io/formats/image.js:164` `if ((nodata !== null && v === nodata) || !Number.isFinite(v)) …`
- 原因の見立て: バンド値は float32 を広げた double、`nodata` はタグ文字列を `parseFloat` した double。文字列が float32 の正確な十進表現でない（丸めてある）と両者がビット一致せず `v === nodata` が偽になる。-9999 のような小さな整数の nodata では一致するが、float の番兵（-3.4e38 等）で外れやすい。
- 直し方の案: nodata を一度 Float32（`Math.fround(nodata)`）にしてから比較する、または `Math.abs(v - nodata) <= Math.abs(nodata) * 1e-5` のような許容付き比較にする。
- 確度: 再現済み（丸めた nodata 文字列のとき。full precision の文字列なら一致する）
- 再現スクリプト: `$W/regress/node/readers.mjs`（A12-tif-nodata）
