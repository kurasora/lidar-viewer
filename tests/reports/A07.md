### 状態遷移（主プロセス `Live.mode` と画面 `LV.src`）
```
 [閉] ─live:open─▶ [開: 1 秒ごとに探す・知らせを聞く]
                     │ LiDAR「表示」(startLidar: stopAll → 設定命令 ×最大10回/300ms → mode=lidar)
                     ├──────────────▶ [LiDAR 受信] ─配信ON─▶ [LiDAR 受信＋配信] ─配信OFF─▶ [LiDAR 受信]
                     │ 配信「表示」(startPeer: stopAll → ws 接続 → mode=peer)
                     ├──────────────▶ [配信を見る] ─ws close（配信元が止める/閉じる）─▶ [開]
                     │ デモ「表示」（画面だけ）
                     └──────────────▶ [デモ]
   どの状態からも: 止める（stopAll）→ [開]／別の「表示」→ stopAll を挟んで切り替え
   横から入る出来事: LiDAR が消える/戻る/IP が変わる、ポートの取り合い、ネットワークの変化、配信元の線が抜ける、壊れた/偽の知らせ・箱
```

### 自作の道具（`$W/regress/lib`）
- `mid360sim.js` … 公開仕様と SDK2 のソースから**独立に**書いたにせ MID-360（アプリの `packCmd` を使わず CRC も自前）。検出の返事をブロードキャスト（本物の仕様）/ユニキャスト（tools/fake_mid360.js と同じ）/サブネット宛てで返す、返事なし・返事のコード・番号違い、点の型 1/2/3、値を照合できる決まった点（grid）・輪（ring）・廊下の地図（map）、取りこぼし・入れ替え・重複・壊れた箱、毎秒の点数、設定の問い合わせ（0x0101）。受けた命令を記録する。
- `drvsim.py` … livox_ros_driver2（SDK2）と同じソケットの作り方（SO_REUSEADDR・設定ファイルの host_ip に bind・200 MB の受信バッファ）でポートを持つ。SDK2 と同じく LiDAR の送り先を自分にする（`--configure`）。
- `attacker.js` … 同じ LAN の悪意のある相手（大きなメッセージ・ゆっくり送るフレーム・受け取らない相手・偽の知らせの洪水・偽の検出の返事の洪水・壊れたメッセージを送るにせの配信元）
- `livepc.js` … `live.js` の Live を 1 台の「PC」として標準入力で操作する
- `probe_mid360.js` … 本物の MID-360 を調べる道具（実験室用。検出の返事の出し方・今の送り先・点群の箱の中身を記録して、最後に元へ戻す）
- netns: Node の試験は `a07`（a071〜a075 = 10.107.0.1〜5）、画面の試験は `a07u`（10.117.0.x）、耐久は `a07e`（10.127.0.x）。同時に動いても混ざらないよう組を分けた

### A07-002 [重大] 同じ LAN のロボット（livox_ros_driver2＋FAST-LIO）が使っている LiDAR を「表示」すると、ロボットへの点群が止まり、「止める」でも戻らない（警告も知らせもない）
- 種類: 意図しない挙動（安全に関わる）
- 対象: アプリ version（全 OS）
- 再現手順: LiDAR（a071）、ロボット役（a074。SDK2 と同じソケットの作り方で、SDK2 と同じく LiDAR の点群の送り先を自分 10.107.0.4 に設定）、アプリ（a072）。アプリでその LiDAR を「表示」→「止める」。自動: `regress/t/steal.js`
- 期待される結果: ロボットの受信を妨げない。少なくとも「この LiDAR はほかの PC（10.107.0.4）に送っています。表示すると、そちらには届かなくなります」と確かめ、止めたら元の送り先へ戻す
- 実際の結果: ロボットの受信 542 箱/秒 → 表示した瞬間に **0 箱/2 秒**（S2）。止めても **0 のまま**（S3、LiDAR の送り先は 10.107.0.2 のまま）。一覧には「使用中」などの表示もない（S1）
- 証拠: `$W/logs/steal.txt`
- 場所: live.js:142-162（`start` が 0x0006 を無条件に書き換える）、live.js:163（`stop` は戻さない）
- 原因の見立て: MID-360 の点群はユニキャストで 1 か所にしか送れない（仕様の 0x0006 pointcloud_host_ipcfg。マルチキャストは可）。livox_ros_driver2 は LiDAR を最初に見つけたときに 1 回だけ設定を送る（SDK2 general_command_handler.cpp `UpdateLidarCfg` → `devices_` にある間は送らない）ので、奪われても自分では取り戻さない。走行中のロボットなら FAST-LIO の入力が黙って止まる
- 直し方の案: つなぐ前に 0x0101（設定の問い合わせ）で 0x0006 を読み、ほかの IP なら確認の窓を出す。止める・アプリを閉じるときに元の送り先へ戻す。複数の PC で同時に見たいならマルチキャスト（SDK2 の `multicast_ip` と同じ）を選べるようにする
- 確度: 再現済み（にせ LiDAR・SDK2 を模したプロセス）。送り先が 1 つなのは仕様どおりなので本物でも同じはず。実機で要確認（試験の資産「実機」の 3）
- 再現スクリプト: `$W/regress/t/steal.js`

### A07-003 [重大] livox_ros_driver2（Livox SDK2）が同じ PC で動いていると、「ポートが使われています」の知らせが出ず、点が 0 のまま（ドライバをあとから起動しても黙って 0 になる）
- 種類: バグ（出ない知らせ）
- 対象: アプリ version。Linux で再現。Windows・macOS は資料からの推定
- 再現手順: 同じ PC で `drvsim.py --mode sdk2 --host-ip <PC の IP>`（SDK2 の network_util.cpp と同じく、すべてのソケットに SO_REUSEADDR を付けて設定ファイルの host_ip に bind）を動かしてから、ライブのカードを開いて LiDAR を「表示」。自動: `regress/t/ports.js`、画面は `regress/t/ui2.js`
- 期待される結果: 「ポート 56301 がほかのソフト（livox_ros_driver2 など）に使われています」のような知らせ（このアプリにはその文言がある）
- 実際の結果:
  - D1（ドライバが先）: `open()` の errors は空。「表示」を押すと 3 秒待って「LiDAR から設定の返事がありません」（直後に上書きされて見えない＝A07-005）、点は 0。LiDAR の返事 10 回と点の箱はすべてドライバ側へ（1,046 箱/2 秒）
  - D2（アプリで受信中にドライバを起動）: 521 箱/秒 → **0**。知らせなし、`errors` も空
  - D6（ドライバが host_ip を "local"＝0.0.0.0 にしてあとから起動）: あとから bind した方がすべて受ける（アプリ 0）
  - D7（ドライバが先・0.0.0.0、アプリがあと）: 今度はアプリが受け、**ドライバ側が 0**（ロボットの SLAM が黙って止まる向き）
  - 知らせが出るのは、相手が SO_REUSEADDR を付けていないとき（D3・D4）だけ
- 証拠: `$W/logs/ports.txt`、`$W/logs/ui2.txt`
- 場所: live.js:65-73（`bindUdp` の `reuseAddr: true`）、live.js:105（EADDRINUSE のときだけ案内）
- 原因の見立て: Linux では両方が SO_REUSEADDR なら bind が成功し、ユニキャストは「より細かい bind（特定 IP）」か「あとから bind した方」にだけ届く。
  Windows: libuv 1.46 は UDP の reuseAddr に SO_REUSEADDR を使う（src/win/udp.c）。Windows の SO_REUSEADDR は「使用中のポートに強制的に bind でき、どちらに届くかは不定」（Microsoft「Using SO_REUSEADDR and SO_EXCLUSIVEADDRUSE」）。SDK2 の Windows version も SO_REUSEADDR なので、同じく黙って取り合いになると推定。さらに相手が何も付けずにワイルドカードで持っていると、同じ資料の表（Windows Server 2003 以降）では WSAEACCES になり、コードは `EADDRINUSE` しか見ないので「bind EACCES 0.0.0.0:56301」のような英語がそのまま出る（コード上の推定）。
  macOS: libuv は SO_REUSEPORT を使う（src/unix/udp.c `uv__set_reuse`）ので同様に取り合いになる（推定。ただし macOS 用の livox_ros_driver2 はほぼない）
- 直し方の案: LiDAR 用のポートは `reuseAddr: false` にして、取り合いを bind の失敗として知らせる（Windows の EACCES も同じ案内に）。SDK2 があとから SO_REUSEADDR で来る場合は防げないので、点や返事が来ないときに「同じ PC で livox_ros_driver2 などが動いていませんか」と出す
- 確度: Linux は再現済み。Windows・macOS はソースと資料からの推定
- 再現スクリプト: `$W/regress/t/ports.js`、`$W/regress/t/ui2.js`、`$W/regress/lib/drvsim.py`

### A07-004 [重大] 配信 ON のあいだ、同じ LAN のだれでも認証なしでつなぎ、配信元の主プロセスのメモリを数百 MB 単位で使わせられる（大きさ・数・時間の上限がない）
- 種類: セキュリティ（DoS）
- 対象: アプリ version（配信 ON のとき）
- 再現手順: 配信 ON の PC（a072）に、同じ LAN（a075）から `attacker.js` でつなぐ。自動: `regress/t/sec.js bigmsg slowframe stuck hold`
- 期待される結果: 配信元は相手から何も受け取らないので、大きなメッセージは即座に切る。つなぐ数にも上限がある
- 実際の結果:
  - 90 MB のメッセージを 4 本同時（I1）: 主プロセスの RSS **88 → 531 MB**、主プロセスが最大 **1.4 秒止まる**
  - 長さ（90 MB）だけ申告して 1 MB ずつ送るフレーム × 6（I2）: **277 → 638 MB**（届くまで ws がため込み、時間切れなし）
  - 時間をずらして受け取りを止めた相手 16 台（I3）: **94 → 217 MB**（1 台あたり約 8 MB）
  - つなぐ数に上限なし（I4、300 台つながる）
  - 本数を増やせば PC のメモリを使い切って落とせる（試験はマシンを守るため 4〜16 本で止めた）
- 証拠: `$W/logs/sec2.txt` `$W/logs/sec3.txt`
- 場所: live.js:221（`new WebSocket.Server({ port: 0 })` が既定のまま: maxPayload 100 MiB、全 NIC で待ち受け、認証・台数・時間切れなし）、live.js:240（8 MB までため込む）
- 原因の見立て: 配信元は相手からのメッセージを使わないのに、ws の既定（100 MiB まで受け取る）のまま。知らせ（UDP 47800）を聞いた人ならだれでもつなげる
- 直し方の案: `new WebSocket.Server({ port: 0, maxPayload: 1024, verifyClient })`。verifyClient で台数の上限（例 8）と、知らせに乗せた使い捨ての合言葉（URL の `?k=…`）を確かめる。ping/pong で返事のない相手を切る。ため込む上限を時間で決める（A07-0SLOW を参照）
- 確度: 再現済み（Node の Live＝主プロセスと同じコード、Electron 34 の Node）
- 再現スクリプト: `$W/regress/t/sec.js`、`$W/regress/lib/attacker.js`

### A07-006 [中] 「止める」のあとも LiDAR は PC へ送り続け、アプリは 5 つの UDP ポートをアプリを閉じるまで放さない
- 種類: 意図しない挙動・資源

### A07-0RACE [中] 返事を待っている間（最大 3 秒）にほかの配信を押すと、状態が食い違い（mode='lidar' のまま配信を表示）、生の英語のエラーが出る

### A07-0SUBNET [中] LiDAR が PC と別のサブネット（工場出荷の 192.168.1.1xx など）のとき、PC の有線 LAN に既定の経路がないと LiDAR が見つからず、「IP を 192.168.1.50 に」の案内も出ない
