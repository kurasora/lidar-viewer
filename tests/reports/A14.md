### A14-001 [重大] 自動の水平補正が、MID-360 のふつうの取り付け高さ（0.5 m 以上）の地図で天井を「床」とし、天井が z = 0 になる
- 種類: バグ
- 対象: 両方（アプリ version・試作ページ）
- 再現手順:
  1. `python3 $W/regress/gen/gen_fastlio.py $W/files/fastlio`（MID-360 を高さ 0.55 m に載せたロボットで、天井 2.7 m の廊下を走った FAST-LIO 風の地図 scans.pcd）
  2. 既定の設定（「開いたときに自動で水平にする」「床を z = 0 にする」がオン）のまま scans.pcd を開き、「補正」のカードを見る
- 期待される結果: 床の高さ ≈ -0.55 m（センサーの高さぶん下）を検出し、床が z = 0 になる
- 実際の結果: 「傾き 4.26° を補正 / 廊下の向きに合わせて 6.9° 回転 / **床の高さ 2.155 m → 0 m**」。天井が z = 0、本当の床は z = -2.7 になる。
  箱の上面（床から 0.8 m）の Z は -1.9 と表示され、高さの色分け・断面の位置・情報の「範囲 z」もすべて天井基準になる。
  センサーの高さ 0.30 m では正しく、0.55 / 0.80 / 1.20 m では天井を選ぶ（S1b の表）。付属の sample/map.laz（センサーが低い）では正しいので、開発中は気づきにくい
- 証拠: `$W/out/c1_01_map.png`、`level_check.js` の出力（S1b）
- 場所: src/worker.js:364-395（analyze の 3. 床の高さ、387 行の `sm[b] >= 0.1 * mx`）
- 原因の見立て: 床の山を「最大の山（＝天井）の 10% 以上で最も低いもの」としているが、MID-360 は下向きの視野が -7° しかなく、床の点は天井の 1.5〜7% しか写らない（S1b）。10% に届かないので床の山が候補から外れ、天井の山が残る
- 直し方の案: 山の大きさを「点の数」ではなく「その高さの層が覆う水平の面積（xy の格子、例えば 0.5 m 角の数）」で比べる（床は点がまばらでも天井と同じ広さを覆う）／
  面の法線の向きを、センサーのいた側（地図の原点＝走り始めの位置や軌跡）に向けてそろえ、上向き（床）と下向き（天井）を分けて数える／
  FAST-LIO の地図なら原点がセンサーの位置なので「原点より下の最初の大きな層」を床とする／床と天井の候補の間が 1.8 m 以上あれば下側を床とする（app.js の findCeiling と同じ考え）
- 確度: 再現済み（アプリ version・Chromium）
- 再現スクリプト: `$W/regress/level_check.js`、`$W/regress/c1_money.js`

### A14-002 [重大] 天井を隠したまま点をクリックすると、見えていない天井の点が選ばれる（座標・距離の両方）
- 種類: バグ
- 対象: 両方
- 再現手順:
  1. 床の検出が正しく働く地図 `$W/files/floor_h0.3/scans.pcd`（または付属の sample/map.laz）を開く（「天井を隠す」は既定でオン）
  2. 「視点」→「上」で真上から見る。「座標」を入れて、床の上の箱の上面（床から 0.8 m）や床をクリックする
  3. 「距離」で、箱の横の床 → 箱の上面 を測る
- 期待される結果: 画面に見えている点（床・箱）が選ばれる。距離は「高さの差 +0.80」前後
- 実際の結果: 選ばれるのは光線が最初に当たる「隠れている天井」の点。S1 では箱の上面のクリックで Z = 0.013（天井）、床 → 箱の距離が「0.519 / 水平 0.519 / 高さ +0.00」（両端とも天井の点）。
  印（球）は奥行きを無視して描かれるので、画面上は正しい所に印が出て、間違いに気づけない
- 証拠: `$W/out/c1_03_pick_top_ceilhidden.png`、`$W/out/c1_05_measure_top.png`、`c1_money.js` の出力 measureObj（両端の z が 2.85・2.84 = 天井）
- 場所: src/app.js:1185-1189（pick の問い合わせに天井の面 uCeilN / uCeilD を渡していない）、src/worker.js:155-160（visible は切り出しの箱しか見ない）
- 原因の見立て: 天井を隠すのは描画（頂点シェーダの `dot(uCeilN, w) > uCeilD`）だけで、点を選ぶ別スレッドの判定には入っていない
- 直し方の案: pick の問い合わせに `ceil: useCeil ? { n, d } : null` を加え、worker の visible() で `n·w > d` の点を除く（断面・切り出しと同じ扱い）
- 確度: 再現済み（アプリ version）
- 再現スクリプト: `$W/regress/c1_pick_hidden.js`

### A14-003 [重大] ライブで LiDAR を「表示」すると、ロボットの ROS2 ドライバ（FAST-LIO）への点群が黙って止まり、閉じても戻らない
- 種類: 意図しない挙動（実験室での使い方で危険）
- 対象: アプリ version（全 OS）
- 再現手順（にせ LiDAR・netns、`$W/regress/live/c9_coexist.sh`）:
  1. LiDAR（.1）・ロボットの PC（.2、livox_ros_driver2 の代わりが「送り先 = 自分」を設定して受信中）・ノート PC（.3）を同じスイッチにつなぐ
  2. ノート PC の LiDAR Viewer で「ライブ」→ LiDAR の「表示」
- 期待される結果: ほかの PC に向いている点群を横取りするなら、その前に知らせて確かめる。やめたら元の送り先に戻す（または、送り先を変えずに見られる方法を選べる）
- 実際の結果: LiDAR の送り先がノート PC に書き換わり、ロボットのドライバに届く箱が毎秒 1,890 → 0。LiDAR Viewer で「止める」・終了しても戻らない（ドライバを起動し直すまで FAST-LIO に点群が来ない）。画面には何も知らせが出ない。
  IMU の送り先（0x0007）は書き換えないので、ロボットには IMU だけが届き続け、FAST-LIO は点群なしで IMU だけで姿勢を進めて地図が崩れるおそれがある（確度: コード上の推定）。
  同じ PC で動かした場合も、ドライバが SO_REUSEADDR でポートを開いていると、**ライブのカードを開いただけで**ドライバへの箱が 0 になる（エラーも出ない）。
  SO_REUSEADDR なしなら「ポート 56101 がほかのソフト…に使われています」と出るが、逆に LiDAR Viewer が先にカードを開くと、ポートをアプリ終了まで離さないため、あとから起動したドライバが EADDRINUSE で起動できない
