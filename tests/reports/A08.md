## 脅威分析（STRIDE）

### 守るもと（資産）
- 利用者のパソコン（主プロセス = Node 権限で動く。落ちる/固まる/任意コードが動くと影響大）
- 画面に表示する点群データの正しさ（座標・点数・色）
- 同じ LAN 上での点群データの機密（配信は本来「見せてよい相手」にだけ）

### 入口（attack surface）
1. **開くファイルの中身**（PCD/PLY/LAS/E57/… 82 形式）。ファイル名・ヘッダーの項目名・属性名・宣言サイズが攻撃者の制御下。ドラッグ&ドロップ or「開く」。
2. **ネットワーク（ライブ機能, 主プロセス側 live.js）**。同じ LAN の第三者が UDP/WebSocket で到達:
   - UDP 56000 検出応答（なりすまし装置）
   - UDP 56301 点群注入（送り手 IP 無検査）
   - UDP 47800 配信ビーコン（なりすましで被害者を攻撃者サーバへ誘導）
   - WebSocket 配信（攻撃者サーバ → 被害者。PCV1 フレーム）
   - 被害者が立てる配信 WS（認証なし・全 IF に開く）
3. **IPC**（preload 経由 `window.pcdLive`）。レンダラが乗っ取られた場合の主プロセスへの二次攻撃面。
4. **配布物**（asar・chrome-sandbox・署名）。
5. **試作ページ**（claude.ai アーティファクト, 外部送信の有無）。

### 攻撃者モデル
- A: 悪意ある点群ファイルを被害者に開かせる（メール・共有）。
- B: 同じ LAN 上の第三者（研究室・学内 Wi-Fi）。認証が一切ないライブ機能に直接パケットを送れる。
- C: レンダラの XSS 等でコードが動いた場合に IPC を叩く(二次)。

### STRIDE 要約表（詳細は各指摘へ）
| 脅威 | 該当箇所 | 指摘 |
|---|---|---|
| S なりすまし | 配信ビーコン(47800)・検出応答(56000)・点群(56301) に認証/送信元検査なし | A08-002, A08-005 |
| T 改ざん | 配信 PCV1・注入点群で表示点群を偽装 | A08-002, A08-005 |
| R 否認 | （ローカルアプリにつき対象外） | — |
| I 情報漏えい | 配信 WS が認証なしで全 IF に開く → 同 LAN の誰でも点群受信 | A08-004 |
| D サービス妨害 | 悪意 PCV1 で主プロセス即クラッシュ / 解凍爆弾 / ビーコン洪水 | A08-001, A08-003, A08-006 |
| E 権限昇格 | CSP で JS 実行は阻止されるが HTML 注入は成立（スクリプトレス） | A08-002 ほか |

## 試験の計画
1. ネットワーク: 悪意 PCV1 → 主プロセスクラッシュ（最優先, netns/loopback で実機確認）
2. ファイル注入: PCD FIELDS 等の項目名が innerHTML に無エスケープで入る（ブラウザ harness で実証）
3. 解凍爆弾: PCD binary_compressed の usize 過大宣言（harness + MEM 見張り）
4. IPC 引数検査: live:share の step=0/負/NaN、open 前呼び出し
5. Electron チェックリスト照合（F12・権限ハンドラ・sender 検査）
6. 依存部品の既知脆弱性（Electron 34 / ws / three ほか）
7. 配布物（asar 中身・chrome-sandbox・mac 署名）
8. 試作ページの外部送信

## 見つけた問題

### A08-001 [致命] 配信の悪意フレーム（PCV1 の点数を巨大に）で主プロセスが即クラッシュ
- 種類: セキュリティ（ネットワーク起点の DoS）
- 対象: アプリ版（ライブ機能。全 OS）
- STRIDE: Denial of Service / Tampering
- 再現手順:
  1. 攻撃者は被害者と同じ LAN で WebSocket 配信サーバを立て、UDP 47800 に `{app:'pcd-viewer', port:…}` のビーコンを流す（or A08-002 のなりすまし）。
  2. 被害者がライブのカードで「ほかのパソコンの配信」からその配信を選ぶ（＝ライブ機能の本来の使い方）。
  3. 接続直後、攻撃者は先頭 'PCV1'、点数 n=0xFFFFFFFF の 8 バイトを送る。
  - 実証: `$W/poc/poc_a_pcv1_crash.js`（攻撃者 WS サーバ + 被害者 Live を子プロセスで起動し、本物の `live.js` の `ws.on('message')` を通す）
- 期待される結果: 壊れたフレームは無視し、ログに出す程度でアプリは動き続ける。
- 実際の結果: 被害者プロセスが未捕捉の `RangeError: Invalid typed array length: 12884901885`（live.js:213）で終了（終了コード 1）。Electron ではこれは主プロセス＝アプリ全体の異常終了。
- 証拠: `$W/evidence/A-001_pcv1_crash.txt`
- 場所: `live.js:209-213`（`decodeBatch`: `new Float32Array(copy.buffer, off+8, 3*n)` が n を無検査で使う）／`live.js:311`（`ws.on('message', d => { const b = decodeBatch(d); … })` が try/catch なし）
- 原因の見立て: 配信フレームの n（点数）と実バッファ長の整合を検査せず、巨大 n で TypedArray 生成が RangeError。さらに message ハンドラが未捕捉。
- 直し方の案:
  - `decodeBatch` で `if (buf.length < 8 + 13*n) return null;`（n が負/巨大/不整合なら捨てる。`n` は `>>>0` で整数化、上限も設ける）。
  - `ws.on('message')` を try/catch で囲い、例外時はフレーム破棄＋ログ。
  - 併せて `ws.on('error')` だけでなく主プロセスに `process.on('uncaughtException')` の最後の砦を検討。
- 確度: 再現済み
- 再現スクリプト: `$W/poc/poc_a_pcv1_crash.js`（`node poc/poc_a_pcv1_crash.js`）

### A08-002 [中] ファイルの項目名（PCD FIELDS 等）が画面に無エスケープで注入される（HTML インジェクション）
- 種類: セキュリティ（保存型 HTML 注入／XSS 未遂）
- 対象: 両方（アプリ版・試作ページ。全 OS）
- STRIDE: Tampering / (Elevation は CSP が阻止)
- 再現手順:
  1. 悪意ある PCD を作る（`$W/poc/mal/xss_fields.pcd`）。FIELDS 行に複数トークンを置く:
     `FIELDS x y z <img src=q onerror="window.__xss=1"><h2>injected</h2>`
  2. アプリ/試作ページでこのファイルを開く。
  - `header.fields.join(' ')`（app.js:1541）がトークン間に空白を戻すため、`<img … onerror=…>` が丸ごと再構成される。
  - 実証: `$W/poc/poc_c_xss.js`（本番の dist/index.html を Chromium で開いて #info の DOM を検査）
- 期待される結果: 項目名もファイル名同様にエスケープ（app.js:1538 の `escapeHtml(f.name)` と同じ扱い）。
- 実際の結果: #info 内に実体の `<img>` と `<h2>injected</h2>` 要素が生成された（注入成立）。**ただし** CSP に `'unsafe-inline'` がないため onerror は実行されず（`window.__xss` 未定義、コンソールに "Refused to execute inline event handler …"）。#fieldSel（app.js:518）・分類凡例（app.js:492）も同様に無エスケープ。
- 証拠: `$W/evidence/C-xss_info.txt`
- 場所: app.js:1541（`${f.header.fields.join(' ')}`）、app.js:518（`<option value="${n}">${n}</option>`）、app.js:492（`${S.field} = ${v}`）。いずれも `escapeHtml` を通していない。発生源: `src/io/formats/pcd.js:15,84`（FIELDS を小文字化のみ）→ `worker.js:429` header.fields。PLY の property 名・LAS 拡張次元名・E57/SHP/DXF の属性名も同じ `sink.field(name)`→header.fields 経路で同様の恐れ（要追加確認）。
- 影響（CSP で JS 実行が止まっても残るもの）: `style-src 'unsafe-inline'` が許可されているため、項目名から `position:fixed` の全画面オーバーレイ（`$W/poc/mal/xss_overlay.pcd`）を注入して偽の「更新」ボタン等でクリックを誘導する、凡例/情報欄の表示を偽装する、`<a>` で誤誘導する、等のスクリプトレス攻撃は依然成立しうる。
- 原因の見立て: ファイル名と形式名はエスケープしているが、項目名の経路だけ漏れている（実装の抜け）。
- 直し方の案: 1541/518/492 を `escapeHtml(...)` 経由にする（`f.header.fields.map(escapeHtml).join(' ')`、option の value/text、凡例の `escapeHtml(S.field)`）。恒久対策として CSP に `'unsafe-inline'` を style-src からも外し、注入点を無くす。
- 確度: 再現済み（JS 実行は CSP により不成立、HTML 注入は成立）
- 再現スクリプト: `$W/poc/poc_c_xss.js poc/mal/xss_fields.pcd`

### A08-003 [中] PCD binary_compressed の展開サイズ（usize）が上限（cap）に縛られず、解凍爆弾でメモリを食い尽くす
- 種類: セキュリティ（解凍爆弾 / 資源枯渇）
- 対象: 両方（PCD 読み込み。全 OS）
- STRIDE: Denial of Service
- 再現手順:
  1. `$W/poc/gen_lzf_bomb.mjs` で ~11MB の binary_compressed PCD を生成（展開後 ~1.0GB、増幅率 約88倍、実データ点数は 10 点）。
  2. 読み込ませる（`read.mjs` 経由＝本番の `src/io/formats/pcd.js` を使用）。
- 期待される結果: 「読み込む最大点数（cap）」の範囲でメモリが収まる／宣言サイズの検査で拒否。
- 実際の結果: cap と無関係に `new Uint8Array(usize)` を確保し LZF 展開で実際に書き込むため、800MB の見張りを超えて停止（終了コード137、ピーク~808MB）。実アプリではワーカー（＝レンダラ）が同量を確保し、RAM の少ない環境で OOM。
- 証拠: `$W/evidence/B_bomb_info.txt`（ファイル情報）、`$W/evidence/B_bomb_run.txt`（guard 137）
- 場所: `src/io/formats/pcd.js:66-71`（`usize = getUint32(4)` → `lzfDecompress(comp, usize)`、cap 未参照）、`src/pcd.js:38-39`（`new Uint8Array(outLen)`）
- 補足（実測）: 確保だけでは RSS は増えない（V8 は 4GB 確保も遅延。`$W/poc/probe_alloc.mjs` で確認）。実害は LZF が実際に書き込む分で、増幅率は本デコーダの構造上 ~88 倍が上限。よって「極小ファイル→即OOM」ではなく「~数MB→数百MB〜GB」級。
- 直し方の案: `usize` を `cap * stride` 程度の上限と `csize` との比（増幅率上限）で検査して拒否。`lzfDecompress` の outLen にも上限。`n*stride > cap*stride` の時点で早期に点数上限を考慮。
- 確度: 再現済み
- 再現スクリプト: `$W/poc/gen_lzf_bomb.mjs` → `read.mjs`

### A08-004 [中] 配信 WebSocket が認証なし・全インターフェースに開き、同じ LAN の誰でも点群を受信／大量接続できる
- 種類: セキュリティ（情報漏えい + DoS）
- 対象: アプリ版（ライブ配信。全 OS）
- STRIDE: Information Disclosure / Denial of Service
- 再現手順: `$W/poc/net/run_share.sh`（netns a08。a081 が `Sharer` で配信、a082 が攻撃者）
  1. 配信側（a081, 10.108.0.1）が配信を開始（`WebSocket.Server({port:0})` は 0.0.0.0 で待受）。
  2. 攻撃者（a082, 10.108.0.2）が `ws://10.108.0.1:<port>` に接続。資格情報・トークン・確認ダイアログは一切なし。
- 期待される結果: 配信先を限定する／少なくとも接続時に利用者へ確認・表示、接続数の上限。
- 実際の結果: 認証なしで接続でき、点群フレーム（17 フレーム×100 点、実座標を含む）を受信。さらに 40 本の追加接続もすべて確立（接続数の上限なし）。
- 証拠: `$W/evidence/E-share_noauth.txt`
- 場所: `live.js:221`（`new WebSocket.Server({ port: 0 })` = 全 IF）、`live.js:237-241`（`send`: 接続数の制限なし、送信可否は bufferedAmount だけ）
- 原因の見立て: LAN 内共有を簡単にする設計だが、アクセス制御が皆無。学内 Wi-Fi など不特定多数と同一セグメントだと、環境の点群（＝室内形状）が第三者に漏れる。多数接続で配信側のメモリ・帯域を消費させられる。
- 直し方の案: 一度きりの共有コード/トークンを beacon ではなく口頭/画面表示で配り、WS 接続時に検証。接続元 IP を同一サブネットに限定する任意設定。接続数の上限。UI に「N 台が受信中」だけでなく接続元の表示と切断ボタン。
- 確度: 再現済み
- 再現スクリプト: `$W/poc/net/run_share.sh`

### A08-005 [中] 配信ビーコン(UDP 47800)・検出(56000)・点群(56301) に送信元の検証がなく、なりすましで被害者を攻撃者サーバへ誘導できる
- 種類: セキュリティ（なりすまし / 改ざん。A08-001 の配送路）
- 対象: アプリ版（ライブ。全 OS）
- STRIDE: Spoofing / Tampering（→ A08-001 の DoS へ連鎖）
- 再現手順: `$W/poc/net/run_beacon.sh`（netns a08。a081 が被害者 `Live.open()`、a082 が偽ビーコン）
  1. 攻撃者（a082）が `{app:'pcd-viewer', name:'EVIL-HOST', port:31337, model:'MID-360', sn:'SPOOFED', id:'evil123'}` を 47800 のブロードキャストに流す。
  2. 被害者（a081）の一覧に、攻撃者が決めた name/model/sn と、攻撃者の IP:port を指す配信が出現。
- 期待される結果: 配信元の正当性を確認する手立て（少なくとも UI で IP を明示し、既知/未知を区別）。
- 実際の結果: 被害者の `finder.list()` に `{address:'10.108.0.2', port:31337, name:'EVIL-HOST', model:'MID-360', sn:'SPOOFED'}` が出現。被害者が選ぶと `ws://10.108.0.2:31337` に接続し、そこで A08-001 の悪意 PCV1 を受けて主プロセスが落ちる。または偽の点群を「本物」として表示（改ざん）。
- 併せて: `live.js:169 onPoints` は受信パケットの送信元 `r` を見ない（56301 への点注入に送信元検査なし→稼働中セッションに偽点を混入可能）。`onDetect`(126) も同様にブロードキャストの応答を無検証で装置一覧に反映。
- 証拠: `$W/evidence/F-beacon_spoof.txt`
- 場所: `live.js:252-262`（PeerFinder: beacon を無検証で peers 化）、`live.js:101,169`（hostPoint の message で `r` 未使用）
- 原因の見立て: LAN 内の善意を前提にした設計で、発信元認証がない。
- 直し方の案: 点群ソケット(56301)は選択中の装置 IP からのみ受理。配信選択時に接続先 IP を明示し確認。ビーコンは参考情報に留め、接続は利用者の明示操作必須（現状そうだが、IP 明示と既知判定を追加）。
- 確度: 再現済み
- 再現スクリプト: `$W/poc/net/run_beacon.sh`

### A08-006 [重大] 同梱の Electron 34.5.8 がサポート終了（EOL）で、未修正の Chromium/V8 脆弱性を抱えたまま配布している
- 種類: セキュリティ（依存部品 / 配布物）
- 対象: 配布物（全 OS）
- STRIDE: Elevation of Privilege（エンジン層の既知脆弱性）
- 調査結果（Web, endoflife.date/electron, 2026-10 時点）:
  - Electron 34 のサポートは 2025-06-23 に終了。最終リリースは 34.5.8（2025-06-04）＝本アプリが使う版。
  - 現在サポートされるのは 42 / 43 / 44（最新 44.8.0, 2026-10-16）。34 は約 16 か月、セキュリティ修正なし。
- 影響: レンダラは contextIsolation・sandbox 有効で緩和されるが、Chromium/V8 に既知の未修正 RCE/サンドボックス回避が存在しうる。悪意ファイル（A08-002/画像/wasm 経路）やレンダラ側の不具合が、古いエンジンの既知バグと組み合わさると被害が拡大。
- 直し方の案: Electron をサポート中の版（44.x）へ更新してビルドし直す。更新を継続的に追う運用。
- 確度: 再現済み（版の確認・EOL の公開情報）／悪用 PoC はエンジン更新前提のため未実施
- 参考: https://endoflife.date/electron
- 依存部品の棚卸し（`npm audit --package-lock-only` 実施, 証拠 `$W/evidence/npm_audit.json`）:
  - **本番依存（配布物に入る）= 0 件**。`ws` は 8.22.0（CVE-2024-37890 修正済みの 8.17.1 以降, OK）。ランタイム wasm/JS: three 0.160.1（古い。最新 ~0.18x。描画用で直接のネットワーク面はなく既知の致命 CVE は見当たらないが更新推奨）、fflate 0.8.3 / geotiff 3.0.5 / laz-perf 0.0.7 / occt-import-js 0.0.23 / web-ifc 0.0.78 / draco3d 1.5.8（いずれも未知入力を解く解析器＝パーサ堅牢性は A03 と分担）。
  - `npm audit` 全体では 19 件（critical 1, high 13, moderate 5）。**うち `electron` は high として検知（A08-006 を裏付け）**。critical の `tar` ほかは electron-builder / node-gyp / cacache 等の**ビルド専用依存**で、**配布物（asar）には含まれない**（A08 確認済み: asar は ws + dist + main/preload/live のみ）。→ ビルド環境のサプライチェーンリスクとして別途更新推奨。

### A08-007 [軽微] IPC `live:share` の step が無検査で、0/負/NaN だと配信時に主プロセスが落ちうる
- 種類: セキュリティ（IPC 引数検査不足 / 堅牢性）
- 対象: アプリ版
- 再現手順: `$W/poc/poc_d_ipc_args.mjs`（`encodeBatch` を step=0/-1/NaN で呼ぶ）

### A08-010 [情報] IPC ハンドラが送信元フレーム（senderFrame）を検証していない

### A08-011 [情報] CSP の評価: 'unsafe-eval'・style の 'unsafe-inline'・base-uri/object-src 未指定・file:// の 'self'
- 種類: セキュリティ（CSP 設計）
- 場所: `src/index.html:6`
- 所見:
  - `script-src` に `'unsafe-eval'`（STEP 展開が eval を使うため）。注入文字列が eval に到達すれば危険だが、現状その経路は見当たらない。
  - `script-src` に `'unsafe-inline'` が無いのは良い（A08-002 の onerror はこれで阻止された）。
  - `style-src 'unsafe-inline'` があるため、HTML 注入が成立する箇所（A08-002）では inline style による全画面オーバーレイ等のスクリプトレス偽装が可能。
  - `base-uri` 未指定（既定は default-src だが base-uri は default-src をフォールバックしないため実質無制限）→ HTML 注入時に `<base>` で相対参照を乗っ取る余地。`object-src` も明示が望ましい。
  - file:// での `'self'` は Chromium で挙動が不安定（厳密には opaque 寄り）。実運用上は script-src が効いているが、`'self'` に依存しすぎない設計が安全。
- 直し方の案: `object-src 'none'; base-uri 'none'` を追加。可能なら STEP 展開を eval 非依存にして `'unsafe-eval'` を外す。style の inline も段階的に削減。

### A08-012 [軽微] Linux 配布物の chrome-sandbox が setuid(4755) でない／AppImage のサンドボックス前提
- 種類: 配布物（Linux）
- 場所: `release/linux-unpacked/chrome-sandbox`・`release/linux-arm64-unpacked/chrome-sandbox`（いずれも 0755, 非 setuid）
- 影響: unprivileged user namespaces が無効なホストでは、sandbox:true の本アプリは起動に失敗、または `--no-sandbox` 運用（サンドボックス無効）に陥る恐れ。deb インストール時に 4755 付与されるかは要確認。AppImage は原理上 setuid 不可で userns 依存。
- 直し方の案: deb のポストインストールで `chown root:root && chmod 4755 chrome-sandbox` を保証。利用案内に userns 要件を明記。実機（各ディストリ）で起動確認。
- 確度: 配布物のパーミッション確認済み／実機起動影響はコード上の推定

### A08-013 [情報] mac 版は ad-hoc 署名（identity:null）で Gatekeeper に阻まれる
