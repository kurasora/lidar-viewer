# A01 点群の形式（ブラックボックス） 報告

（作成中。見つけたものは随時書き足す）

## 試験の計画

### 対象
点群の形式の読み込みの正しさ: PCD／LAS・LAZ／E57／PLY／PTX／ASCII 系（.txt .asc .neu .xyz .pts .csv）／SBF（+.data）／CloudCompare BIN／PN・PV・SOI・OUT・POLY・SX、軌跡（.txt .csv .tum .mcap）、
点数の上限（capSel）での間引き、複数ファイル（同じファイル 2 回・違う形式を同時・原点の違うファイル＝グローバルシフトの共有）、成功・失敗の知らせ。

### 技法
- 同値分割・境界値分析: 形式ごとに「仕様の範囲内の正しいファイル」の変種を Python で作る（型・符号化・欄・順序・区切り・改行・version・点の形式・色の bit 数・座標の大きさ）
- 正解との比較（テストオラクル）: 元の numpy 配列（作った値そのもの）を正解とし、点数・平均・最小・最大・個々の点（座標→色・欄の対応）を比べる。
  形式の解釈が分かれるもの（PLY の float 色、PTX、SBF、BIN、PN/PV/SOI/OUT/POLY/SX）は CloudCompare 2.11.3（実物、または同じ version のソース）とも比べる。PCD は PCL 1.14 の道具（pcl_convert_pcd_ascii_binary）で書いたものも使う
- デシジョンテーブル: ASCII 系の列の役割の推定（見出しの有無 × 列数 × 値の範囲）
- 状態遷移: ファイルを開く順序と S.offset（グローバルシフト）、閉じたあと
- コードレビュー（静的解析）: src/io/formats/*.js・sink.js・util.js・trajectory.js・app.js の読み込み部分
- 実行の道筋: Node（自作 `node_check.mjs`。速い・LAZ 不可）と Chromium（本番と同じ dist/index.html。自作 `bcheck.js` で座標・色・欄・知らせを取り出す）。最後は必ず Chromium でも確かめる

## 見つけた問題

### A01-001 [重大] 高さの幅が約 6,200（ファイルの単位）を超える点群を開くと、画面の処理が例外で止まり、以後どのファイルも開けなくなる
- 種類: バグ
- 対象: 両方（画面の処理 app.js。アプリ version・試作ページとも同じ）
- 再現手順: 高さ（z）の 0.5〜99.5% の幅が約 6,214 を超える点群を開く。例: 廊下の点群を mm 単位にした `$W/regress/data/pcd/coord_I4_bin.pcd`（z が -5394〜3132 mm）。続けて普通の点群（`pcd/xyz_f4_bin.pcd`）を開く
- 期待される結果: どちらも開ける（mm 単位の点群や、高低差の大きい地形も表示できる）
- 実際の結果: 1 つ目でページに `RangeError: Maximum call stack size exceeded`（findCeiling ← updateCeiling ← updateBounds ← onLoaded）。知らせは出ず、視点も合わない。2 つ目を選んでも何も起きない（読み込みの順番待ちが止まったまま。知らせもなし）。ページを開き直すまで直らない
- 証拠: `$W/exp/dbg1.log`（写しの非圧縮ビルドでのスタック）、`$W/regress/out/browser/pcd/coord_I4_bin.json`（errors）、場面試験 `tall_then_next`
- 場所: src/app.js:372 `const mx = Math.max(...sm)`（sm は 5 cm 刻みのヒストグラム。幅 6,214 で 124,277 本を超え、Chromium の引数の上限を超える）。例外が onLoaded（app.js:675〜705）の途中で起きるため、最後の `loadNext()` が呼ばれず `loading` が true のまま
- 原因の見立て: 配列を関数の引数に展開している（`Math.max(...sm)`）。高さの幅に比例して本数が増える
- 直し方の案: `let mx = 0; for (const v of sm) if (v > mx) mx = v;` のようにループで求める（本数にも上限をつける）。onLoaded の中の処理を try/finally で囲み、何があっても `loadNext()` と知らせを出す
- 確度: 再現済み（Chromium。Chromium での上限は `$W/exp/spread_limit.js` で測定: 124,277 本 ≒ 高さの幅 6,214）
- 再現スクリプト: `$W/regress/bscenario.js`（場面 `tall_then_next`）

### A01-002 [重大] グローバルシフトが「1 つのファイルの最初の点」だけで決まるため、最初の点が原点付近（無効な 0,0,0 の点など）で残りが地図座標の点群は、座標が 10 cm 以上ずれる
- 種類: バグ（黙って座標が誤る）
- 対象: 両方（Sink は Node・画面とも同じ）
- 再現手順: `$W/regress/data/las/first_origin_then_utm.las`（最初の点だけ 0,0,0、残り 4,999 点は UTM 539000/3836000 付近、cm 単位）を開く
- 期待される結果: 1 mm 以内（シフトは点群全体、またはヘッダーの範囲から決める）
- 実際の結果: シフトが [0,0,0] になり、UTM の点が float32 のまま持たれて最大 120 mm ずれる（y の刻みが 0.25 m）
- 証拠: `$W/regress/out/node/las/first_origin_then_utm.json`、compare の出力（`1 mm を超える誤差（最大 120.00 mm）`）
- 場所: src/io/sink.js:54 `if (this.offset === null) this.offset = [x, y, z].map(v => Math.abs(v) >= BIG ? Math.round(v / 100) * 100 : 0);`
- 原因の見立て: 最初の点だけを見てシフトを決めている。LAS のように頭書きに範囲（最小・最大）や offset がある形式でも使っていない
- 直し方の案: LAS は頭書きの最小・最大（または offset）でシフトを決める。そのほかは「シフト 0 のまま |x|≥1e4 の点が来たら、そこで初めてシフトを決め直す（それまでの点はまだ小さいので引き直しても精度は落ちない）」か、最初の N 点の中央値で決める
- 確度: 再現済み（Node。画面でも確認予定）
- 再現スクリプト: `$W/regress/run.sh`（試験 id `las/first_origin_then_utm`）

### A01-004 [中] LAS の色が 8 bit か 16 bit かを「先頭 2 万点」だけで決めるため、先頭に色のない点（0,0,0）や暗い点が多いと、残りの点の色が黒・でたらめになる
- 種類: バグ（黙って色が誤る）
- 対象: 両方（LAS・LAZ）
- 再現手順: 16 bit の色（仕様どおり 0〜65535）の LAS で、先頭 2 万点の色がすべて 255 以下（色の付いていない 0,0,0 の点が先頭にある場合など）のものを開く。
  `$W/regress/data/las/rgb16_first20k_black_x256.las`（先頭 2 万点が 0,0,0、残り 5,000 点は 8 bit×256 の色）、`…_black_raw16.las`（残りが 16 bit の生の値）、`…_dark.las`（先頭 2 万点が 0〜255/65535 の暗い色）
- 期待される結果: 16 bit として読む（残り 5,000 点は元の色、先頭の暗い点は黒に近い）
- 実際の結果: 8 bit とみなされる。×256 の色は下位 8 bit だけが残ってすべて黒（`色が違う点 5000 個（例: 読んだ [0,0,0] 正解 [54,60,216]）`）、生の 16 bit の値はでたらめな色、暗い点は 256 倍明るくなる（`色が違う点 20000 個`）。×257 で書いた色は、下位 8 bit が上位と同じなので偶然正しく見える
- 証拠: `$W/regress/out/node/las/rgb16_first20k_*.json`、`out/node.txt`
- 場所: src/io/formats/las.js:57-63（rgbShiftOf）・78 行（最初の塊の 2 万点だけで判定）、110 行（LAZ も最初の 2 万点）
- 原因の見立て: 判定に使う点が先頭に偏っている。さらに 8 bit とみなしたあとに 255 を超える値が来ても Uint8Array に入れるときに下位 8 bit に切り捨てられる
- 直し方の案: ファイル全体から等間隔に選んだ点（例: 2 万点）で最大値を見る。あるいは 16 bit のまま一時的に持ち、読み終えてから最大値で 8 bit/16 bit を決めて変換する。少なくとも 255 を超える値が出たら 16 bit に切り替える
- 確度: 再現済み（Node。画面でも確認予定）
- 再現スクリプト: `$W/regress/run.sh`（試験 id `las/rgb16_first20k_*`）

### A01-007 [軽微] E57: Integer の項目で minimum / maximum の属性が省かれている（既定 = int64 の全範囲）と、値がすべて 0 になる
- 種類: バグ
- 対象: 両方
- 再現手順: `$W/regress/data/e57/int_default_range.e57`（intensity が Integer、範囲の属性なし。libE57Format は既定値の属性を書かない）を開く
- 期待される結果: 強度が元の値（0〜2016）
- 実際の結果: すべて 0（`欄 intensity の値が違う点 4908 個（例: 読んだ 0.0 正解 492.0）`）

- 確度: 再現済み（Node）。実際にこの書き方をする書き手は少ない
